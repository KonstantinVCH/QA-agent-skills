# Эталоны блоков отчёта

Эталоны взяты из реальных комментариев команды, принятых читателями; предметная область заменена
на вымышленный интернет-магазин (`order-service`, `payment-service`, `catalog-service`,
`notification-service`), структура и формулировки сохранены. `{…}` — плейсхолдеры.

## Содержание

1. Эталон 1 — сводная таблица пофикшенных багов
2. Эталон 2 — настройки стенда и предусловия
3. Эталон 3 — пошаговый отчёт о прогоне
4. Эталон 4 — компактный отчёт о прогоне (форма по умолчанию)
5. Скелет блока «Что проверить на проде»
6. Markdown-вариант для чата

||№||Заголовок||Фактический результат (до фикса)||Коммит фикса||
|*БАГ-2*|Карта переходов заказа запрещала {{NEW → REJECTED_FRAUD}} — антифрод-отказ падал с {{ORDER.ERR.0021}}|Консьюмер {{antifraud.check}} не мог проставить отказной статус: в логе {{{}ERR_0021 «Переход из статуса NEW запрещён»{}}}, заказ навсегда оставался {{NEW}}|[bd9645e|{BITBUCKET_URL}/projects/{PROJECT}/repos/order-service/commits/bd9645e94157…]|
|*БАГ A*|Решение платёжного шлюза не доставлялось в order-service: публикация в direct-обменник с пустым routing key|0 доставок за всю жизнь очереди ({{{}publish_in=2/out=0{}}}); слушатель {{PaymentDecisionListener}} не вызывался ни разу. Чем хорош: масштаб в цифрах, доказательство фикса в той же строке, коммиты кликабельны,
несколько коммитов на один баг — через `+`.

## 3. Эталон 3 — пошаговый отчёт о прогоне (стиль коротких шагов)

```
1. Пользователь создан методом users/register, статус NEW
2. Вызван /order/create
3. По ссылке произошёл редирект на экран «Подтверждение личности» (внешний провайдер не подключён) — корректно
   /delegated-check/authorizationCheckClient
   {JAEGER_URL}/trace/f00b9903125f0bcd9df830b1a0613db7?uiFind=b70eb702713f1f5e

Пройден процесс подтверждения личности + регресс для процесса «Делегированная проверка».
Поправлены тест-кейсы, прикреплены к задаче.
```

Чем хорош: шаги читаются за 10 секунд, каждый — с результатом, трейс ведёт сразу на нужный
спан, в конце — что закрыто и что стало с тест-кейсами.

## 4. Эталон 4 — компактный отчёт о прогоне (форма по умолчанию)

Форма по умолчанию, когда сессия — прогон проверок, а не череда фиксов. Шапка не пишется: ни
«Задача: …», ни «Настройки стенда», ни «Предусловия» — если они не несут информации, без которой
прогон не повторить. Отчёт начинается сразу с таблицы.

```
h1. PROJ-123 — результаты тестирования

||Что проверялось||Как проверялось||Итог||Результат||
|Отчёт формируется, если по заказу уже есть отчёт по другому способу доставки|подменил тип у существующей записи на «самовывоз», запустил формирование за 21.04|(/)|отчёт создан; до правки не создавался ни один, [трейс|{JAEGER_URL}/trace/…]|
|Повторный запуск не создаёт второй отчёт|запустил формирование дважды подряд|(/)|второй раз «заказов не найдено», записей не добавилось|
|Отчёты по подарочным картам|посмотрел текст выборки для подарочных карт|(!)|признака способа доставки нет — проблема осталась, см. находку 1|
|Заказ без заполненного типа доставки|запустил формирование на таком заказе|(x)|{{HTTP 500, SHOP.ERR.9999}}, см. находку 2|

h2. Находки

*1. <Что именно, одной фразой>.* <Развёрнутое пояснение.> <Что с этим делать и кому.>

*2. <Что именно>.* {{HTTP 500, SHOP.ERR.9999}}, [трейс|{JAEGER_URL}/trace/…]. Ожидался <X>, получено <Y>.
Поведение было до этой задачи — приёмку не блокирует, нужна отдельная задача.

h2. Не проверено

Постаматы, курьерская доставка и подарочные карты.

h2. Итог

Дефект исправлен, подтверждено на стенде. <Одна фраза про регресс.> Стенд оставлен чистым:
временные изменения возвращены, содержимое таблицы совпадает со снимком до начала работ.
```

Чем хорош и что копировать:

* **Никакой шапки.** Название задачи известно из самого тикета, стенд и коммит — из блока
  настроек, только если их меняли. «Предусловия» — лишь когда без них прогон не воспроизвести.
* **Четыре столбца, ничего лишнего.** «Как проверялось» — одна человеческая фраза: что я сделал
  руками. «Итог» — значок, видный при беглом просмотре. «Результат» — что получилось и чем доказано.
* **Строки таблицы — про продукт, а не про механику.** «Отчёт по самовывозу не мешает
  курьерскому», а не «TC-7 проверка additional_info».
* **Находки вынесены под таблицу**, в таблице — только «см. находку N». Иначе ячейка разрастается
  и таблица перестаёт читаться.
* **«Не проверено» — одной строкой перечислением.** Развёрнутые причины нужны, только если
  спросят; в отчёте они превращаются в оправдания.
* **Итог — три предложения:** что с дефектом, что с регрессом, что со стендом.

## 5. Скелет блока «Что проверить на проде»

Скелет показывает форму; запросы пишутся под конкретную задачу.

```
h2. Что проверить на проде

*Главная проверка* — дублей отчётов по одному заказу и способу доставки нет:
{code:sql}
select order_id, delivery_type, report_date, count(*)
from reports.delivery_report
where report_date >= date '{дата выкатки}'
group by order_id, delivery_type, report_date
having count(*) > 1;
{code}
Ожидаемо пусто. Строка здесь означает, что заказ отчитался дважды по одному способу доставки.

h3. До выкатки
 # Объём риска — сколько активных заказов без типа доставки: {{select count(*) from …}} → ожидаемо {N}; больше — новые записи без типа, сообщить аналитику.
 # …

h3. После выкатки
 # Новая логика работает — отчёты за первый день созданы по всем способам доставки: {{select …}} → ожидаемо не ноль по каждому.
 # …

h3. Где запрос может соврать
 * {{order_id}} пересекается между витринами — фильтровать по {{shop_id}}.
 * {{delivery_type}} заполняется асинхронно, в первые минуты после создания заказа он ещё пустой.
```
