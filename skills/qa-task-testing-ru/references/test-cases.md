# Тест-кейсы по итогам прогона

Читай на Шаге 8.5. Работа с Allure TestOps через API (шаги деревом, общие шаги, вложения, кастомные
поля, связь с задачей) — скилл `allure-testops-cases-ru`; если он установлен, заводи кейсы по нему.
Здесь — правила содержания, которые действуют в любой системе тест-менеджмента.

## Запрет на создание без разрешения

**Не создавай тест-кейсы и не заводи папки / структуру под них, пока человек явно и однозначно не
ответил «да, создавай» на прямой вопрос.**

«Сделай / проверь / прогони» — не разрешение создавать тест-кейсы. Разрешено: анализ, поиск
существующих, черновик кейса текстом для показа. Создание в системе — только после явного «да».

*Урок:* восемь тест-кейсов завели без разрешения, с выдуманной структурой, часть — с данными,
которых на стенде не существовало. Запрет навсегда.

**Структуру не выдумывай.** Формат берётся few-shot из эталонных тест-кейсов проекта и регламента
команды (`references/project-config.md`, раздел 8). Название, description, предусловия и шаги
оформляй по эталону, а не по своему усмотрению.

## Сначала искать, потом создавать

Дубли — обычный исход поспешного создания. Порядок:

1. Открой каталог тест-кейсов проекта, если он ведётся (страница базы знаний или выгрузка).
2. Поищи в системе по Story / Feature / тегу задачи (в Allure TestOps — RQL / AQL, например
   `cf["Story"] = "payments"`).
3. Нашёл похожий → **обнови существующий**, не плоди новый.
4. Новый функционал → возьми Layer / Feature / Story из существующей структуры, не изобретай новые.

**Ищи не только по названию.** Кейс может называться абстрактно («Оплата картой для юрлиц»), а
реальный флоу — сообщение в очередь, запросы, UI — виден только в шагах сценария и description.
Поиск только по названию теряет большую часть затронутых кейсов: при необходимости выгрузи все
кейсы вместе с шагами и ищи по полному тексту. Перед выводом «кейса нет» прочитай scenario и
description найденных кандидатов.

Ловушки инструментов (встречались в Allure TestOps, проверь у себя):

- `list`-методы с параметром `search` могут **не фильтровать по подстроке**, а возвращать
  последние по дате — используй поиск с RQL / AQL.
- RQL может **не работать с кириллицей** в значениях — фильтруй по латинским Story / Feature либо
  читай весь список Story.
- Чтение сценария может вернуть пустой список шагов, хотя шаги есть (хранятся в другом
  представлении) — читай через UI или REST напрямую.

## Оформление сценария — жёсткое правило

**Шаг сценария = ТОЛЬКО действие. Ожидаемый результат = ТОЛЬКО результат.**

Запрещено в шагах и ожидаемых результатах: история бага или фикса («до фикса было…»), «эталонный
трейс: …», «регресс-критерий», «доказывает, что…», «граница включена», «это принятое поведение»,
любые пояснения и справки. Это живёт только в description и во внешних ссылках (трейс, коммит
фикса).

Формат:

- **Шаг:** «Выполнить POST <URL> с телом из вложения "<имя>.json"» или «Выполнить SQL из вложения
  "<имя>.sql"».
- **Ожидаемый результат:** HTTP-код + тело ответа либо конкретные значения в БД. Например:
  `HTTP 422 {"code":"ORDER.ERR.0014",...}` или `status = 'PAID' во всех 4 строках, updated_at
  проставлен`.
- Длинные SQL и payload — во вложения. Однострочный SELECT можно текстом шага.

### Description — одно предложение

**Description = одно предложение по шаблону команды (например, «Тест-кейс направлен на проверку
<чего именно>») + ссылки на документацию — и всё.**

Конкретная логика (что, где, при каких условиях должно получиться) идёт в ожидаемый результат
последнего шага, а не в description. Пример ожидаемого результата: «Во всех 4 таблицах адресов
клиента записи обновлены: значения равны переданным в теле запроса, `address_type = 'DELIVERY'`,
`updated_at` проставлен».

Запрещено в description: методология («негатив доказывается в паре с контрольным позитивом»),
внутренний жаргон, пересказ шагов, история бага и фикса.

Пример хорошей формулировки: «Тест-кейс проверяет, что при отсутствии поля `externalId` во входящем
запросе существующие значения в 4 таблицах адресов клиента СОХРАНЯЮТСЯ».

### Атомарность — жёстко

Один тест-кейс = одно поведение. Не гоняй несколько состояний или вариантов в одном сценарии «для
компактности».

Антипаттерн: «возраст < 18 → ошибка валидации», «без даты рождения → ошибка валидации», «ровно 18 →
200» в одном кейсе — это **три** отдельных кейса (такой кейс удалили на ревью).

Сигнал нарушения: у каждого шага свой финальный ожидаемый результат разного класса. Разбивай так:
негативы отдельно (эквивалентные вариации одного поля можно в один кейс), позитивная граница —
всегда отдельный кейс.

## Остальные элементы

- **Название:** короткое, суть, без префикса сервиса.
- **Предусловия:** воспроизводимое состояние (SQL создания). **Откат фикстур в шаги не включай** —
  откат живёт только в рабочем протоколе прогона.
- **Данные предусловий проверь SELECT-ом по реальной БД стенда ДО оформления.** Не создавай кейс с
  непроверенными id: кейсы, ссылающиеся на несуществующие на стенде заказ и клиента, уже
  приходилось переделывать.
- **Обязательно:** тег или связь с задачей + внешняя ссылка на трейс реального прогона.
- **Кастомные поля:** в Allure TestOps надёжнее всего массовая установка в режиме `replace`; id
  полей — в `references/project-config.md`, раздел 8.
- **Статус нового кейса:** по соглашению команды (по умолчанию — Review, не Draft, чтобы кейс
  попал на ревью).

## Ловушки API Allure TestOps

| Проблема | Что делать |
|---|---|
| MCP-инструменты не пишут сценарий | писать шаги через REST (для мануальных кейсов — в дерево шагов, а не в сценарий автотестов: он в UI не виден) |
| Обновление кейса затирает внешние ссылки | после обновления восстановить ссылки отдельным вызовом |
| Кириллица в имени вложения бьётся через curl | загрузить, затем переименовать отдельным PATCH |
| Чтение сценария отдаёт пустой список | читать через REST / UI, а не через MCP |

## После создания или обновления

Обнови каталог тест-кейсов проекта, если он ведётся, — иначе следующий поиск не найдёт кейс и цикл
дублей повторится.
