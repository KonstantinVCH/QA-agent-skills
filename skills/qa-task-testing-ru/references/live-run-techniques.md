## 1. Публикация сообщения в очередь (RabbitMQ inject)

Перед публикацией:

1. Прочитай JSON-схему сообщения — типы полей строго по ней.
2. Возьми образец payload из span-лога producer'а в реальном трейсе, если он есть.
3. Узнай обязательные заголовки. Для Spring AMQP это обычно `__TypeId__` — полное имя класса
   события, по которому consumer десериализует сообщение. Без него или с опечаткой consumer
   отбросит сообщение молча или с ошибкой конвертации.
4. Подготовь фикстуры и откат (см. `references/preconditions-and-test-data.md`).

Где публиковать: RabbitMQ management → Exchanges → нужный exchange → Publish message, либо HTTP API
management (`POST {RABBITMQ_URL}/api/exchanges/{vhost}/{exchange}/publish`). Пример параметров:

```
Exchange:     orders.events
Routing key:  orders.payment.confirmed
Headers:      __TypeId__ = com.example.orders.event.PaymentConfirmedEvent
Properties:   content_type = application/json
Payload:      { полный JSON, без сокращений }
```

Результат проверяй через 15–20 секунд (consumer может быть асинхронным, с ретраями и задержкой).
После каждой публикации заполни карточку воспроизведения `assets/repro-card.md`.

## 2. Логи и тела запросов из трейсинга

Бывает, что на стенде нет `kubectl` (нет kubeconfig), нет доступа к Kibana / OpenSearch / Grafana
Loki и к RabbitMQ management. Прогон и снятие логов всё равно возможны через **трейсинг + curl + БД**.

Проверь, прикрепляет ли трейсинг к спанам логи приложения (level / logger / message / thread) и
тела HTTP-запросов и ответов (например, Logbook). Если да — WARN/ERROR/INFO сервиса и тела
запросов читаются прямо из сырого Jaeger API, pod-логи не нужны.

```bash
# трейс целиком; логи лежат в data[0].spans[].logs[].fields[]
curl -fsSL "$JAEGER_URL/api/traces/{traceId}" -o trace.json

# поиск по окну времени (микросекунды, UTC)
S=$(date -u -d "YYYY-MM-DD HH:MM:SS" +%s)000000
E=$(date -u -d "YYYY-MM-DD HH:MM:SS" +%s)000000
curl -fsSL "$JAEGER_URL/api/traces?service={TRACE_SERVICE_PREFIX}{service}&operation={op}&start=$S&end=$E&limit=800" -o traces.json
```

- Сохраняй трейс в файл и ищи по нему (`logs[].fields[].message`), а не тяни весь JSON в контекст.
- **Тело запроса для воспроизведения** бери из span-лога «Incoming Request … POST … {body}» — не
  реконструируй вручную.
- Операции `consumer` / `producer` — обобщённые спаны очередей. Повторные и отложенные сообщения
  могут лежать в **отдельных** трейсах: ищи по окну времени, а не внутри одного трейса.
- MCP трейсинга падает с 500 — иди напрямую через curl: обёртка ломается, когда недоступен backend
  хранения трейсов.
- Для логов подов в OpenSearch — скилл `opensearch-logs-ru`.

## 3. Детерминированное форсирование ветки кода через БД

Если retry-цикл или условие в коде **только опрашивает** состояние (SELECT), а не переинициирует его,
ветку «исчерпания / провала» можно форсировать, **удерживая** значение в БД так, чтобы опрос всегда
промахивался.

Пример: дату проверки документа держали на «вчера» фоновым циклом (UPDATE каждые 2 секунды),
перебивая разовую перепроверку внешним сервисом, которая иначе проставила бы «сегодня». Так
стабильно воспроизводилась ветка «проверка не готова после N попыток».

Обязательный порядок:

1. Прочитай код ветвления: что именно опрашивается и когда пишется.
2. Зафиксируй эталон отката.
3. Прогон.
4. Останови фоновый цикл, выполни откат, проверь чистоту SELECT-ом.

## 4. Имена полей на границе сервисов

Когда значение течёт producer → (очередь / HTTP JSON) → consumer / маппер, имя поля проверяй **с
обеих сторон**. Рассинхрон даёт `null` без единой ошибки — фича молча не работает.

Проверь три вещи:

- как поле называется в модели, которую заполняет **producer** (JSON-схема / DTO общей модели);
- какое поле **читает** маппер consumer'а (например, MapStruct `@Mapping(source = "source.x")`);
- какое имя **реально уходит** в сообщении — из span-лога producer'а в трейсе.

**SNAPSHOT-дрейф между открытыми ветками.** Consumer, собранный против раннего SNAPSHOT общей
модели, может компилироваться со старым именем поля, тогда как producer уже шлёт новое — в рантайме
`null`. Пример: в общей модели поле `paymentValidationResultMessageId`, маппер адаптера читает
`source.messageId` — значение теряется. Что producer шлёт длинное имя, подтверждает span-лог.

## 5. camelCase или snake_case в JSON

Имя поля в JSON определяет стратегия сериализации, а не только аннотация `@JsonProperty`. Проверь:

1. `spring.jackson.property-naming-strategy` в конфиге сервиса;
2. переопределяет ли общий билдер HTTP-клиента (WebClient / RestTemplate) свой `ObjectMapper` —
   если нет, работает дефолтный `ObjectMapper` Spring Boot;
3. эмпирику — существующий unit-тест, который проверяет сериализованный JSON (например,
   ассерт `{"orderId":...}` означает camelCase).

Не додумывай: без одного из трёх доказательств пиши HYPOTHESIS.

## 6. Упал деплой — читай состояние Deployment, а не только лог сборки

Лог сборки CI показывает симптом, но он не всегда принадлежит текущему запуску. Два места, где
легко ошибиться.

**Провал может быть чужим.** Инструмент деплоя (Ansible, Helm) применяет спеку; если она не
изменилась, ответ `changed=false`, а объект Deployment сохраняет условия от предыдущей попытки.
Сверяй отметки времени: `managedFields[].time` и `conditions[].lastTransitionTime` (в UTC) против
времени сборки. Если `ProgressDeadlineExceeded` встал раньше старта прогона — этот прогон лишь
досидел свои `progressDeadlineSeconds` и пересказал чужой провал. Перезапуск даст ровно то же.

**Кто именно не поднялся.** При `maxUnavailable: 0` старый под остаётся жив, поэтому условие
`Available: True` и стенд отвечает — но на прежней версии. Признаки настоящего провала: `replicas`
больше `readyReplicas`, `unavailableReplicas: 1`, имя ReplicaSet в сообщении
`has timed out progressing`. Логи фильтруй по префиксу пода именно этого ReplicaSet, иначе в выборку
попадут записи двух версий сразу.

**Ссылка на логи из лога сборки бесполезна как есть**, если в ней зашито относительное окно
(`time:(from:now-15m,to:now)`), а смотрят позже. Подставь абсолютное окно в UTC вокруг отметки
провала (переведи локальное время в UTC).

Если упала миграция БД — смотри логи Job мигратора: сообщение «Application startup failed» у
сервиса бывает следствием, а не причиной.

Порядок разбора: состояние Deployment → логи пода за нужное окно (раскрывай поле со стектрейсом —
в `message` видна только первая строка) → только потом гипотезы о причине. Обратный порядок уже
приводил к неверным выводам.

Ошибки уведомлений плейбука (мессенджер, дашборды, предупреждения о синтаксисе инвентаря) — обычно
шум, к падению отношения не имеют. Список известного шума — `references/project-config.md`,
раздел 6.

## 7. Как добыть traceId

- Из ответа API с ошибкой — поле с traceId (какое именно — `references/project-config.md`, раздел 6).
- Из успешного ответа — поиском трейсов по сервису, операции и окну времени
  (`jaeger_find_traces` в MCP или `GET $JAEGER_URL/api/traces?...&lookback=10m`) и сопоставлением по
  времени прогона и числу спанов.
- Перед публикацией убедись, что трейс существует и его `hasError` соответствует утверждению.
