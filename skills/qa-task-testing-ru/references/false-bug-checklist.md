# Чеклист «не ложный ли это баг»

Пройди его перед каждым выводом BUG и перед каждым баг-репортом. Ложный баг хуже ненайденного: он
тратит время команды и подрывает доверие к QA.

## Чеклист

- [ ] **Состояние данных РОВНО исходное.** SELECT до прогона показал ожидаемое состояние, а не грязь
      от предыдущих прогонов и неполных откатов (служебные и hash-поля тоже вернулись).
- [ ] **Есть контрольный позитив** — тот же сценарий с валидными данными работает. Или **контрольное
      сравнение** — другой провайдер / флоу на тех же данных ведёт себя иначе.
- [ ] **Все ошибки всех трейсов цепочки разобраны по тексту лога** и классифицированы: не ENV и не
      тестовые данные, а логика.
- [ ] **Требование прочитано в коде или спеке.** Порядок строго: факт → требование → расхождение → BUG.
- [ ] **Типовые ловушки тестовых данных исключены:** контрольные суммы идентификаторов, реальные коды
      справочников, формат UUID, значения enum из кода, а не из БД.
- [ ] **Тело и параметры тест-запроса сверены с РЕАЛЬНЫМ вызовом** (трейсы других стендов, лог
      «Incoming Request»): не пропущено ли поле, которое в проде шлёт вызывающий.
- [ ] **Код смотрели по ветке задачи** и на стенде задеплоена именно она (контрольный вызов).
- [ ] **Получатель жив.** Если находка «сообщение не доходит до X» — проверено, что X этот
      топик/очередь ещё читает и канал не устарел.

Пункт про сверку тела с реальным вызовом спасает от целого класса ложных багов: пропущенное
опциональное поле → null внутри сервиса → ложный NPE/500, который создал ты сам.

**Причина — это найденный root cause, а не первая правдоподобная догадка.** Если установлен скилл
`systematic-debugging` — ищи причину по нему. Root cause не найден → статус HYPOTHESIS, репорт как
BUG не пишется.

## Антипримеры ложных багов

- **«Синхронизация профиля не обновляет имя покупателя».** Артефакт грязного состояния после
  четырёх прогонов подряд с SQL-откатами: откат не вернул hash-поле, сервис видел «не изменилось».
  Чистый парный прогон на исходном клиенте опроверг баг.
- **«Уверен на 100%: 500 в получении документов клиента».** Тестер слал подтверждение заказа
  тест-телом без `clientId`, а маппер берёт `clientId` из тела — null создал сам тестер. Реальные
  вызовы на других стендах `clientId` передают. Подтверждение механизма (null → 500) ≠
  доказательство, что null возникает в реальном флоу.
- **«Деактивация при совпадающей дате — баг».** Названо BUG без чтения сервиса, где это правило
  явно описано. Требование не прочитали — расхождения не было.
- **«Сообщения не доходят до системы отчётности».** Две находки ушли в работу, а получатель этот
  канал уже не читал — канал устарел. Находки оказались техдолгом, а не багами задачи.

«Уверен на 100%» — только после исключения тестовых данных и с прямым доказательством, а не после
подтверждения одного лишь механизма.

## Если сомневаешься

Сделай чистый одиночный прогон на гарантированно исходном клиенте: новый клиент или клиент, чьё
состояние ты только что проверил SELECT-ом целиком. Цепочке прогонов с откатами не доверяй.
