# База знаний проекта — что читать до, что записать после (опционально)

Применяй, если у проекта есть база знаний: Obsidian-хранилище по паттерну LLM Wiki, вики-раздел
QA, папка заметок в репозитории. Ведение графа (шаблоны страниц, ссылки в обе стороны, каскадное
обновление, журнал операций) — скилл `obsidian-llm-wiki-ru`. Здесь — только QA-специфика.

Базы нет — пропусти Шаг 0 и Шаг 8.6, но всё, что ниже сказано про «записать», сохрани в рабочий
файл сессии `{QA_ROOT}/PROJ-123/RESULT.md`: прогон должен быть воспроизводим.

## Шаг 0 — что прочитать до любых запросов к внешним системам

Цель — не тратить время и токены на то, что уже известно.

1. Обзорную страницу архитектуры (например, `wiki/overview.md`) — всегда первой.
2. Поиск по ключу задачи `PROJ-123` — прошлые сессии, связанные находки.
3. Заметку каждого затронутого сервиса (например, `wiki/entities/{service}.md`).
4. Поиск по термину или паттерну задачи — рус + англ + аббревиатура.

Нашёл — используй как контекст и пропусти дублирующие запросы. Не нашёл — иди дальше по шагам.
Помни, что знание из базы — **унаследованное**: в выводах помечай его так и перепроверяй фактами.

## Экономия контекста

1. Большие сводные файлы (индекс, общий справочник инфраструктуры) не читай целиком — только
   поиском по нужному разделу.
2. Нужен один факт из заметки сервиса — ищи поиском, а не читай заметку целиком.
3. Большие трейсы сохраняй в файл и ищи по нему, а не тяни в контекст.
4. Не читай один файл дважды — используй контекст сессии.
5. Поиск по широкому слову может вернуть сотни тысяч символов и упасть по лимиту — задавай узкие
   запросы и малый контекст вокруг совпадения.

## Что записать — сразу при чтении

Прочитал страницу документации → тут же обнови заметку сервиса или термина. Не «в конце сессии»:
знание должно жить в базе, а не умирать вместе с контекстом. *Урок:* поведение отмены задачи было
известно из трейса, но не попало в базу до прямого вопроса — следующая сессия начала с нуля.

## Что записать после прогона

Помимо обычного ingest (источник → сущность → термин → ссылки → журнал) в базу обязаны попасть:

- **Все тестовые данные и способ их составления:** каждый payload сообщения, данные моков, id
  сущностей, SQL-фикстуры, исходное состояние клиента (эталон отката), валидные и невалидные
  значения. Формат: payload целиком + пояснение каждого нетривиального поля + что должно
  произойти. Временные файлы сессии удаляются, а прогон должен быть воспроизводим и
  переиспользуем.
- **Реальный код изменения** из карты изменений (`references/change-map.md`, Шаг D).
- **Урок**, если были ловушки: нетривиальные находки, обходные пути, ошибки инструментов.
- **Каталог тест-кейсов**, если кейсы создавались или обновлялись.
- **DOC_GAP**, если код разошёлся с документацией, — явной пометкой, а не в общем тексте.
- **Поправки** к фактам, которые не выдержали самопроверки, — иначе неверный факт всплывёт снова.

## Чтобы записанное нашлось

Значимая сущность или термин (от трёх фактов) — **отдельная страница**, а не абзац внутри чужой.
Обязательны синонимы (`aliases`): русский, английский, аббревиатура, варианты через дефис.
Заголовок = термин + расшифровка. Ссылки в обе стороны.

Перед выводом «в базе нет информации» поищи по 2–3 синонимам, включая английский вариант.
Типичные промахи: страница о провайдере входа не находилась по русскому названию (не было такого
синонима); знание о продуктовой линейке лежало внутри заметки сервиса и не находилось по «тесты
<линейки>» (не было отдельной страницы).
