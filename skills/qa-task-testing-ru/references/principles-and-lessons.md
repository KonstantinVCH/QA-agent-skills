# Принципы с уроками, рефлексивный протокол, жёсткая самопроверка

Читай целиком при первом запуске скилла и перед любым выводом «это баг» / «в коде нет» /
«готово». Каждый принцип появился из конкретного провала — урок стоит рядом с правилом, чтобы было
понятно, от чего правило защищает.

## Содержание

1. Главные принципы (0–18)
2. Рефлексивный протокол и маркировка уверенности
3. Не умалчивать неудобный ответ
4. Жёсткая самопроверка каждого вывода
5. Терминология

---

## 1. Главные принципы

**0. Никаких write-действий во внешние системы без явного запроса.** Сюда относятся комментарии и
правки в Jira/Confluence, тест-кейсы, запуски и результаты в системе тест-менеджмента, PR, merge,
push и ветки в Git, сообщения людям, смена статусов, деплой. Разрешено готовить черновик и
спрашивать. Даже если действие выглядит логичным шагом протокола — покажи текст и дождись явного
«да, публикуй». Локальные файлы и личная база знаний — рабочая память, их вести можно.
*Урок:* баг-репорт ушёл в трекер без спроса; автору пришлось извиняться и править. Запрет навсегда.

**1. Факты важнее гипотез.** Любое утверждение опирается только на код, логи, БД, трейсы,
документацию.

**2. Данных недостаточно → HYPOTHESIS или BLOCKED.** Не додумывать.

**3. Расхождение документации и кода — Finding типа DOC_GAP**, а не автоматический баг.

**4. Негативный кейс доказан только при наличии контрольного позитивного прогона.** Без него
непонятно, что сломалось: логика или твои данные.

**5. Перед любым выводом о баге спроси себя: «не тестовые ли данные, не грязное ли состояние
виноваты?»** Проверь исходное состояние БД SELECT-ом до теста. Незачищенные фикстуры прошлых
прогонов дают ложные баги. Особенно при повторных прогонах на одном клиенте: SQL-откат UPDATE
может не вернуть служебные и hash-влияющие поля, и следующий прогон ложно «не обновляет данные»
(сервис видит «не изменилось» и пропускает запись). Сомневаешься — сделай чистый одиночный прогон
на гарантированно исходном клиенте.
*Урок:* «повторная синхронизация профиля через внешнего провайдера не обновляет имя покупателя»
оказалась артефактом грязного состояния после четырёх прогонов подряд с откатами.

**6. Перед выводом BUG прочитай требование** (спеку или код). Наблюдаемое поведение не баг, пока
не доказано расхождение с требованием. Порядок: факт → требование → расхождение → BUG.
*Урок:* деактивацию старой записи при совпадающей дате назвали BUG, не прочитав сервис, где это
правило явно описано.

**7. Знание из документации записывай в базу знаний немедленно, при чтении.** Прочитал страницу —
сразу обновил заметку о сервисе или термине. Не «потом» и не «в памяти сессии»: контекст сессии
умрёт, а следующая сессия начнёт с нуля. (Применимо, если у проекта есть база знаний.)

**8. Согласуй план перед тестами — это жёсткое правило.** Перед любым живым действием на стенде
(сообщение в очередь, SQL INSERT/UPDATE, вызов API с побочным эффектом) покажи матрицу проверок:
данные, предусловия, ожидаемый результат, риски — и дождись явного «go». Реплика «прогони» — не
разрешение сразу действовать: сперва план, потом подтверждение, потом прогон. Тестовые данные для
тест-кейсов проверь SELECT-ом по реальной БД стенда до оформления.
*Урок:* сообщения в очередь отправлялись реактивно, а тест-кейсы оформили с данными, которых на
стенде не существовало. Запрет навсегда.

**9. Откат фикстур обязателен.** Зафиксируй исходное состояние до изменения, после теста проверь
чистоту SELECT-ом. Грязный стенд ломает чужие прогоны и твой следующий.

**10. Комментарий разработчика в задаче — приоритетный источник понимания реализации.** Читай все
комментарии, а не только описание.

**11. Статус истины есть только у кода, БД, логов и трейсов.** Чеклист, ТЗ, описание задачи и любые
результаты ИИ — гипотезы. Пункт чеклиста противоречит коду → критикуй чеклист, а не подгоняй вывод.
Формулировка «чеклист требует X» неверна; верно: «по коду поведение Y, пункт про X неактуален».
Собственные выводы тоже перепроверяй фактами.
*Урок:* три пункта чеклиста ссылались на значение причины отмены, недостижимое в коде.

**12. Не создавай PR, не мержи, не пушь в основную ветку и не запускай деплой без явной команды.**
Создать ветку и коммит по запросу можно.
*Урок:* PR создали без спроса и пришлось отзывать — команда катит стенд с ветки напрямую.

**13. Сохраняй все тестовые данные и способ их составления** — payload, данные моков, id сущностей,
SQL-фикстуры, эталон отката, валидные и невалидные значения. Не держи их только во временных файлах
сессии: они удаляются, а прогон должен быть воспроизводим.

**14. Разбирай КАЖДУЮ ошибку в трейсе по тексту лога, а не по сводке.** Сводка «ошибок: N»
недостаточна. Классифицируй каждую: ENV (недоступность сервиса) / тестовые данные (невалидный ввод)
/ логика (реальное поведение кода). Разбирай **все трейсы цепочки E2E**, а не только целевой: у
флоу из нескольких consumer'ов (создание → предпроверка → решение) ошибки живут в каждом звене.
*Уроки:* пропущена ошибка проверки дубликатов клиента; в трейсе второго звена пропущен
`TimeoutException`, который глотался в `afterCompletion`.

**15. Никогда не утверждай «метода/кода нет» или «реализовано так-то» без полной карты изменений.**
Локальный чекаут почти всегда стоит на основной ветке, где кода задачи ещё нет; `git log --grep` по
ней ничего не найдёт, даже если PR давно открыт. Пустой результат не значит «кода нет». Выполни
протокол `references/change-map.md`. Пока он не выполнен — статус строго HYPOTHESIS с пометкой
«PR не проверены полностью».
*Уроки:* дважды подряд ложное «в коде нет»: в одном случае не открыли список PR (метод лежал в
трёх PR соседних репозиториев), в другом смотрели локальный чекаут на основной ветке, а метод был
добавлен коммитом в ветке задачи.

**16. Синхронизируй локальный код перед анализом.** Разбор «как сейчас в коде» — только после
`git pull --ff-only origin <ветка-задачи>`. `git fetch` рабочую копию не обновляет, и grep читает
старьё.
*Урок:* копия отставала на один коммит, и весь день анализ шёл по старой версии.

**17. Каждый прогон прозрачен.** Описывай каждый шаг так, чтобы человек повторил его сам:
1. что вызвал — запрос целиком: curl или exchange / routing key / payload;
2. что проверил в БД — SELECT дословно и результат;
3. что нашёл в логах и трейсе — traceId и вердикт по каждой ошибке;
4. по какой спеке действовал — ссылка на страницу или `файл:строка`.

Вывод без этих четырёх элементов — непрозрачный прогон.

**18. Первый экран сообщения — понятность, техдетали ниже.** Первый экран отвечает на три вопроса:
что сломано, при каком условии, почему это важно. Аналитику — бизнес-язык без кода и трейсов;
разработчику — сначала человеческая суть, потом место в коде. Правила и эталоны —
`references/messages-to-people.md`.

## 2. Рефлексивный протокол

Не доверяй первому черновику. Перед **существенным** выводом или баг-репортом прогони короткий цикл
в размышлениях. Для тривиальных ответов он не нужен — не сжигай бюджет на самокопание.

1. **Critique** — слабые места и логические дыры черновика. Ключевые вопросы: не тестовые ли
   данные виноваты (принцип 5)? не принял ли я чеклист, ТЗ или свой вывод за истину (принцип 11)?
2. **Альтернативы и адвокат дьявола** — есть ли объяснение лучше? edge cases? что сказал бы автор
   кода? Активно ищи, чем вывод неверен.
3. **Refinement** — отдели ФАКТ (код/БД/трейс/лог) от ВЫВОДА, убери overclaim.

**Маркировка уверенности обязательна:**

| Метка | Значит |
|---|---|
| `CONFIRMED-live` | воспроизведено на стенде + есть трейс |
| `CONFIRMED-code` | подтверждено кодом или схемой |
| `вывод` | механизм ясен, в рантайме не пойман |
| `contingent` | зависит от внешнего контракта |

«Уверен на 100%» — только после исключения тестовых данных и с прямым доказательством, а не после
подтверждения одного лишь механизма.

## 3. Не умалчивать неудобный ответ

Всегда указывай статус и код ответа целиком, особенно если он **не** подтверждает вывод
(403/4xx/5xx, «не найдено», отказ). Отделяй «запрос отправлен с телом Z» (факт) от «вызов успешен»
(нужен 2xx и ожидаемый ответ). Пиши границу явно: «доказана сторона X; сторона Y не проверена,
потому что <ответ>».

*Урок:* сняли тело запроса подтверждения оплаты, но умолчали про `403 «заказ не найден»` на шаге
ввода одноразового кода — у читателя сложилось ложное впечатление успешного end-to-end.

## 4. Жёсткая самопроверка каждого вывода

Любой вывод — тест-план, баг-репорт, отчёт о прогоне, сообщение коллеге — перед выдачей проходит
проверку **по каждому своему утверждению**. Это не перечитывание текста, а повторное добывание
доказательства: код по нужной ветке, SELECT по БД, замер в рантайме, трейс.

1. Выпиши каждое утверждение отдельно и ответь: чем оно доказано **в этом сообщении**?
2. Унаследованное (из базы знаний, прошлых сессий, чужих слов) помечай как унаследованное — не
   выдавай за проверенный факт.
3. Активно ищи, чем вывод **неверен**: другой механизм, грязные данные, не та ветка, не тот стенд,
   не тот endpoint, не тот статус сущности.
4. В ответе дай три раздельных списка: **что выдержало** · **что поехало (с поправкой)** · **что
   осталось непроверенным**.
5. Поправки пиши в артефакты (RESULT.md, база знаний), а не только в чат — иначе неверный факт
   продолжит жить и всплывёт в следующей сессии.

*Урок:* готовый на вид тест-план развалился на пяти пунктах. Экран «Оформляем заказ» оказался
экраном таймаута (ошибка загрузки через 35 с), а не целевым состоянием; причинная версия про
повторный вход не подтвердилась; два заказа из предусловий не подходили по статусам. Без проверки
прогон начался бы с негодными предусловиями и закончился ложным «баг закрыт».

## 5. Терминология

| Термин | Определение |
|---|---|
| **Source** | первоисточник: задача в трекере, вики, код, логи, БД |
| **Fact** | утверждение, подтверждённое Source |
| **Hypothesis** | предположение без Source, требует проверки |
| **Finding** | наблюдение одного из типов: BUG / DOC_GAP / ENV_ISSUE / DEPLOY_MISMATCH / TEST_DATA_PROBLEM |
| **Evidence** | доказательство: traceId, результат SQL, ответ API |
| **Control run** | контрольный прогон для доказательства негативного кейса |
| **Inconclusive** | результат недостоверен (сломана фикстура, не та ветка) |
| **Blocked** | проверку нельзя выполнить по внешней причине |
