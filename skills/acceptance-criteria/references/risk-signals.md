# Матрица рисков — стартовая

Собрана из уроков реальных задач в микросервисной backend-системе (брокер сообщений,
feature-флаги, статусные машины, интеграции с внешними партнёрами). Примеры переписаны на
вымышленный интернет-магазин (`order-service`, `payment-service`, `notification-service`),
механика рисков сохранена.

Матрица стартовая: дополни её разделом «Проектные риски» в `project-config.md` — своими
партнёрами, флоу и уроками. После каждого инцидента добавляй строку: следующий AC подхватит её
сам.

По уровню риска → глубина AC:
- **Критический**: обязательная строка AC (HP или EC), кандидат на ⭐
- **Высокий**: строка AC (EC), если задача затрагивает область
- **Средний**: EC, если релевантно
- **Низкий**: можно опустить

---

## Идентификация и привязка пользователя (Критический)

| Риск | Пример |
|---|---|
| Идентификатор пользователя берётся у фасада, а сохраняется ядром — при сохранении он теряется | `customerId` есть в ответе `shop-api`, но `order-service` при `order/save` его не пишет |
| Асинхронная верификация не обновляет сущность, если не выставлен признак делегирования | внешний провайдер подтвердил личность, а заказ остался `WAITING_VERIFICATION` |
| Разные значения одного справочного кода в соседних флоу | провайдер входа называется `oauth-x` в одном флоу и `oauth-x-lite` в другом — перепутать легко |
| Два вызова создания подряд дают двух разных пользователей | `order/create` дважды → сервис авторизации выдал разные `customerId` |
| Код, симметричный соседним флоу, выглядит подозрительно | одинаковая обработка в трёх ветках бывает намеренным паттерном, а не копипастой-багом — сверить со спекой до репорта |

**EC обязателен:** идентификатор пользователя у фасада совпадает с сохранённым в БД.

## События очередей (Критический)

| Риск | Урок |
|---|---|
| Ответ брокера `{routed: true}` ≠ успешная обработка | ждать 5–6 секунд и проверять БД и consume-спан |
| Триггер срабатывает только при наличии подстроки в поле | уведомление об оплате уходит, только если `paymentPurpose` содержит `orderId`; без него — тишина без ошибки |
| Код типа сообщения в соседних ветках похож | неверный `messageCode` уводит сообщение в чужую ветку обработки |
| Статус вычисляется консьюмером | значение `status` из payload отправки игнорируется — проверять вычисленный, а не отправленный |
| Тип поля в событии | `transactionId` — int, а не string; несовпадение типа роняет консьюмер (`ListenerExecutionFailedException` в Spring AMQP) |
| direct-exchange + пустой routing key | сообщение не маршрутизируется, счётчик publish растёт, ошибки нет нигде |
| В publish-спане нет тега routing key | значит, routing key пустой — искать именно по отсутствию тега |

**EC обязателен:** в трейсе есть consume-спан, а не только publish.

## Feature-флаги (Высокий)

| Риск | Урок |
|---|---|
| Кэш флагов не сбрасывается прямым `UPDATE` таблицы флагов | переключать только через консоль/API управления флагами |
| Функционал за флагом не проверен при выключенном флаге | регресс на проде при выкатке до включения флага |
| Флаг зарегистрирован, но не читается в нужном сервисе | флаг есть в консоли, а код его не видит (не внедрён бин / не тот сервис) |

**EC обязателен:** поведение при выключенном флаге + доказательство, что флаг реально читается
кодом (переключение меняет поведение).

---

## Статусная машина / переходы состояний (Высокий)

| Риск | Урок |
|---|---|
| Невалидный переход не блокируется | валидация перехода должна быть в обоих слоях (фасад и ядро) |
| SQL `UPDATE` статуса без поля версии | безопасен только для таблиц без оптимистичной блокировки |
| «Зомби-статус» для тестов | ручной перевод в служебный статус позволяет достичь любого состояния — годится для демонстрации, но не доказывает реальный флоу |

## Интеграции с партнёрами (Высокий)

| Риск | Урок |
|---|---|
| Изменение в общей логике проверено только на дефолтном партнёре | у партнёров разные анкеты, способы отправки и асинхронные ответы |
| Каскадная отправка | одна заявка уходит нескольким партнёрам параллельно — проверить каждого |

**EC обязателен:** проверка на партнёре, отличном от дефолтного, если изменение в общей логике.
Конкретных партнёров и их особенности впиши в `project-config.md`.

---

## Кэш справочников (Средний)

| Риск | Факт |
|---|---|
| Кэш каталога (Redis и т.п.) | изменения справочника видны только после вызова метода обновления кэша |
| Прямой SQL в справочник | не сбрасывает кэш — нужен вызов обновления или рестарт сервиса |

---

## Идентификаторы и типы (Средний)

| Риск | Урок |
|---|---|
| Внешний идентификатор только строкой | int → HTTP 400 сразу; нечисловая строка → 200 на создании, но 422 на следующем методе |
| Сессия пользователя истекает в длинном флоу | повторная авторизация посреди подписания/оплаты; при повторе — ошибка дубля |
| UUID из error-лога чужого прогона | идентификатор брать из SQL или ответа метода, а не из текста ошибки другого трейса |
| Данные читать у ВЫЗЫВАЮЩЕЙ стороны | обогащение данных живёт в фасаде, проверка только ядра его не видит |

---

## Как обновлять матрицу

После каждого инцидента или урока добавь строку в раздел «Проектные риски» файла
`project-config.md` (или в базу знаний команды). На следующей задаче Шаг 0 и Шаг 2.3 её
подхватят.
