# Артефакты-доказательства (backend)

Скилл рассчитан прежде всего на backend: микросервисы, обмен через брокер сообщений (RabbitMQ,
Kafka), API без UI или с UI, который не меняется в задаче. Артефакт доказывает поведение системы,
а не её внешний вид.

## Что писать в колонке «Артефакты»

Одно из: **traceId** (Jaeger, Zipkin, Tempo — любой распределённый трейсинг), **SQL до/после**,
**HTTP-ответ**, **payload сообщения в очередь**, **CI-пайплайн**, **скриншот консоли флагов**.
Для задач с UI добавляется **скриншот/видео экрана**.

Не раздувать: одна строка AC — один артефакт (или два, если успех и ошибка в одном флоу).

---

## Матрица артефактов по типу изменений

| Тип изменений | Артефакт успеха | Артефакт ошибки / края |
|---|---|---|
| Новый консьюмер очереди / событие | traceId полного флоу без ошибок | traceId с ошибкой |
| Изменение API-эндпоинта | HTTP-ответ 2xx (тело из curl / Bruno / Postman) | HTTP-ответ 4xx/5xx |
| Изменение записи в БД | SQL: SELECT до + SELECT после | SQL: ограничение NOT NULL не нарушено |
| Новый feature-флаг | скриншот консоли флагов + SQL/API-состояние флага | HTTP-ответ при выключенном флаге |
| Новый сервис / модуль | зелёный CI-пайплайн | `GET /actuator/health` (или аналог) |
| Инфраструктура (k8s, Ansible, Helm) | зелёный CI-пайплайн | smoke-запрос curl |
| Изменение интерфейса с партнёром | HTTP-ответ шлюза партнёра success | HTTP 4xx от партнёра |
| Изменение статусной машины | SQL: статус до → после + traceId | SQL: невалидный переход не прошёл |
| Подавление уведомления | SQL: флаг подавления в БД | traceId (спан отправки отсутствует) |

---

## Правила трейса как артефакта

- traceId достаточен, когда весь флоу виден в одном трейсе.
- В AC писать просто **traceId** — ссылку по нему находят сами.
- Доказательство успешной доставки через очередь: в трейсе есть спаны publish И consume.
  Один publish ничего не доказывает — сообщение могло никуда не дойти.
- Доказательство подавления: спан отправки **отсутствует** в трейсе.
- Ошибка в трейсе: признак ошибки у спана + `Caused by` в полном стектрейсе. В кратком поле
  сообщения лога часто только первая строка исключения.

Паттерн проверки:

```
отправка в очередь → подождать 5–6 секунд → найти трейс по operationName / тегу
→ проверить спаны publish + consume → проверить БД
```

## Правила SQL как артефакта

- Всегда «до» и «после» — в одном скриншоте или двух последовательных выводах.
- Читать через MCP-сервер Postgres (если подключён) или клиент БД; запись в БД стенда — только
  тем способом, который принят в команде.
- Прямой `UPDATE` статуса безопасен только для таблиц без оптимистичной блокировки (без поля
  версии, например JPA `@Version`). Для версионируемых таблиц ручной UPDATE ломает следующую
  запись приложения.

---

## Правила HTTP-ответа как артефакта

- Показывать тело ответа, а не только статус-код.
- Bruno / Postman: скриншот вкладки Response.
- curl: вывод `curl -sv ... 2>&1 | head -50`.

---

## Правила ⭐ (прод-смок)

⭐ ставится в номере строки: `1 ⭐`. Строки со ⭐ — то, что проверяют на проде сразу после
выкатки.

Что отмечать:
- **основной happy path** — главный сценарий изменения (обязательно);
- **критичный регресс** — соседний флоу, который может сломаться.

Что НЕ отмечать: пути ошибок, граничные payload, флаги подавления, SQL-проверки без видимого
эффекта.

Ориентир: 1–3 звёздочки на задачу.
