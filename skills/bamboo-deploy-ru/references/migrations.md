# Миграции БД при деплое: пре-чек, починка блокера, непоехавшая миграция

Читать, когда в плане деплоя есть сервис, который везёт Job миграций (Flyway, отдельный
контейнер-мигратор, запускается до старта сервиса). Здесь: как узнать заранее, упадёт ли
миграция на данных стенда; как снять блокер; что делать, если миграция самой задачи на стенд не
поедет. Скрипты: `scripts/migration_precheck.py`, `scripts/migration_fix.py` (Flyway + PostgreSQL,
миграции в Bitbucket Server).

Содержание:
- 0. Есть ли у задачи миграция и кто её повезёт
- 1. Пре-чек данных стенда
- 2. Фикс FK-блокера
- 2a. checksum mismatch
- 2b. Карта классов отказа Job миграций
- 2c. «already exists»
- 2d. В БД есть версия, которой нет в образе
- 2e. Что ещё держать в голове
- 3. Миграция задачи не поедет — подмена образа мигратора
- 4. Проверка, что миграция реально поехала

## 0. Есть ли у задачи миграция и кто её повезёт

```bash
GET {BITBUCKET_URL}/rest/api/1.0/projects/{P}/repos/{migrator}/branches?filterText={TASK}
GET .../repos/{migrator}/compare/changes?from=refs%2Fheads%2F{TASK}&to=refs%2Fheads%2Fmaster&limit=100
#  → пути {migrations-path}/{schema}/V###__*.sql  ⇒  какие схемы затронуты
```

Зачем это знать, хотя катим не мигратор:
- **Миграция задачи может не поехать.** Если Job запускает образ мигратора `latest`, собранный
  из основной ветки, то пока ветка задачи не смёржена, её `V###` в образе нет. Деплой будет
  SUCCESS, а колонок/данных на стенде не появится. Тестировать в таком состоянии бессмысленно:
  получите «баги», которых в задаче нет. Обход — §3.
- **Владелец схемы ≠ автор миграции.** Job носит имя `{service}-migrations` и едет с тем
  сервисом, у которого в конфигурации включены миграции (например,
  `db_migrations_job.enabled: true`). Этот сервис обязан попасть в план деплоя, иначе миграция
  не применится ни при каком количестве прогонов.

## 1. Пре-чек: упадёт ли миграция на данных этого стенда

Job миграций стартует раньше сервиса, живёт до таймаута (часто 600 s × несколько попыток) и
падает не от кода, а от **данных конкретного стенда**: миграция, спокойно прошедшая на стендах
2–3, роняет стенд 1, где остался мусор в таблице. Проверить дешевле, чем узнать через 11 минут
FAILED.

```bash
export DB_PASSWORD='<пароль БД стендов>'          # в аргументах не передавать
export DB_DSN_TEMPLATE='postgresql://app_{stand}:{password}@db.example.com:5432/app_{stand}'
export BITBUCKET_URL=https://git.example.com BITBUCKET_TOKEN='<токен>' MIGRATIONS_REPO=PROJECT/db-migrator
python scripts/migration_precheck.py --stand 1 --schema catalog --task-branch PROJ-123
#   exit 0 → данные пропустят миграции;  exit 1 → блокеры, план в plan.json
```

Что делает скрипт: берёт версию схемы стенда из `flyway_schema_history`, сравнивает со списком
миграций схемы в основной ветке, скачивает **только непримененные** и вытаскивает из их SQL
DDL, который способен не сойтись с данными — `add constraint … foreign key`, `unique`,
`create unique index`, `set not null`. Для каждого генерирует проверочный SELECT и показывает
конкретные строки-нарушители, помечая похожие на мусор прогонов (`is_active=false`,
«тест»/«test»/«stub» в значениях). Заодно печатает, какие миграции задачи отсутствуют в основной
ветке (§0).

Полезные флаги:
- `--branch-migrations` — проверить и миграции ветки задачи: сойдутся ли они с данными стенда
  после мёржа. Дешевле узнать сейчас, чем после подмены образа;
- `--sql-file path.sql` — проверить черновик миграции (её ещё нет в репозитории);
- `--from-version N` — перепроверить уже применённую миграцию (например, понять, чем
  «здоровый» стенд отличается от упавшего).

Ограничение: разбор SQL — регулярками по типовым формам DDL. Экзотический DDL скрипт может не
распознать; если проверить констрейнт не удалось, он скажет об этом прямо, а не промолчит.

## 2. Фикс блокера — и только потом деплой

Найденное — данные общего стенда, а не твои: **покажи строки человеку** (`plan.json` уже
содержит их вместе с признаками) и предложи решение. Правило выбора:

| Что за строка | Решение | Почему |
|---|---|---|
| мусор прогона: `is_active=false`, «тест» в названии, свежий `update_date`, ключ не похож на реальный | **удалить строку** | это мусор тестов; заглушка-родитель под него навсегда осядет в справочнике и попадёт в витрину |
| живые данные: активная запись, старая, с осмысленным ключом | **завести родителя-заглушку** | стенд общий: удаление активной записи ломает чужой прогон ради одной строки в справочнике |
| дубли под `unique`, NULL под `not null` | **руками, с владельцем данных** | «какую из двух строк оставить» — бизнес-решение, автоматике не место |

```bash
# 1) показать план, ничего не меняя
python scripts/migration_fix.py --plan plan.json --stand 1 --stub-parents --delete-test-data
# 2) после «да» — применить
python scripts/migration_fix.py --plan plan.json --stand 1 --stub-parents --delete-test-data --apply
# заглушку лучше копировать со стенда, где миграция уже прошла — так её там уже заводили:
python scripts/migration_fix.py --plan plan.json --stand 1 --stub-parents --reference-stand 3 --apply
```

Гарантии скрипта вместо ручного SQL: без `--apply` только печатает план; удаляемые строки
сохраняет в `backup_<schema>_<timestamp>.json` до изменения; выполняет всё в одной транзакции и
после неё **сам пересчитывает нарушителей** — если хоть один остался, делает `ROLLBACK`:
наполовину применённый фикс хуже непринятого. Ключи для заглушек считает в SQL, а не по
показанным 20 строкам, иначе при массовом мусоре часть ключей осталась бы незакрытой.

Известное ограничение: заглушка-родитель сама может висеть под своим FK (например, партнёр
ссылается на регион). Тогда транзакция упадёт и откатится — придётся заводить цепочку родителей
или удалять строку-сироту. Скрипт скажет это текстом ошибки, не молча.

После успешного фикса — обычный деплой того же релиза. **Релиз пересобирать не нужно**: менялись
данные стенда, а не код.

Пример живого кейса. Миграция V129 навешивала FK `product.partner_code → partner.code` и падала
на стенде 1 с `SQL State 23503`. Пре-чек нашёл две строки-сироты: активный продукт с 2022 года и
выключенную строку «Тест». Активный сохранили через партнёра-заглушку (структура скопирована со
стенда 3, где так уже делали), тестовую удалили с бэкапом — одна транзакция с контрольным
чеком. Повторный деплой того же релиза — SUCCESS за 3 минуты, V129 применена, сирот 0.

## 2a. checksum mismatch — две ветки заняли один номер версии

Симптом в логе пода миграций: `Validate failed: Migrations have failed validation` →
`Migration checksum mismatch for migration version N`. Джоба падает **до** применения чего-либо.
Пре-чек данных тут чист: причина не в строках таблицы, а в истории миграций.

Почему случается: номер `V###` выбирают вручную, и две ветки берут один и тот же. На стенд
успевает приехать вариант из первой ветки (через тестовый тег мигратора), потом образ приносит
вариант из второй — Flyway сверяет контрольную сумму скрипта с записью в `flyway_schema_history`
и отказывается работать.

Разбор за два запроса:
```bash
# что записано на стенде
select version, description, script, checksum, installed_on
from {schema}.flyway_schema_history where version = 'N';
# что несёт образ: файл этой версии в основной ветке и в ветке задачи
GET .../repos/{migrator}/files/{migrations-path}/{schema}?at=refs/heads/{branch}
```
Разные `description`/имена файла при одном номере — диагноз подтверждён.

**Правильное решение — перенумеровать миграцию в ветке задачи** (номер занят), это к разработчику.
**Обходное, чтобы разблокировать стенд** — снять запись версии, тогда Flyway применит вариант из
текущего образа заново:
```bash
python scripts/migration_fix.py --stand N --schema {schema} --checksum-version 130          # план
python scripts/migration_fix.py --stand N --schema {schema} --checksum-version 130 --apply  # снять
```
Скрипт печатает саму запись (description, script, checksum, кто и когда применил), сохраняет её в
`backup_flyway_*.json`, удаляет в транзакции и перепроверяет, что записи не осталось.

⚠️ **Чего обход не делает.** Объекты, созданные удалённой миграцией, остаются в схеме, а записи о
них больше нет — схема и история расходятся. Дальше два исхода, и их надо проверить заранее:
- миграция, которая позже придёт с этим номером, написана идемпотентно (`add column if not exists`,
  `create index if not exists`) → применится поверх и ничего не сломает;
- написана без `if not exists` → упадёт с «column/relation already exists», чинить придётся
  снова (§2c).

Живой случай: номер 130 в одной схеме заняли три ветки сразу. На стенде была применена версия из
одной, приехал образ с другой — mismatch. Запись сняли, деплой прошёл. Колонка, которую добавляла
снятая миграция, осталась в таблице без записи в истории, но та миграция была написана через
`add column if not exists` и после мёржа применилась повторно без ошибки. Это везение, а не
правило: текст миграции проверяют до того, как снимать запись.

## 2b. Карта классов отказа Job миграций и обходы

Сверено с живыми логами мигратора за неделю по всем стендам. Колонка «встречалось» — видели ли
класс в реальности, а не предполагали.

| Класс | Как выглядит | Встречалось | Обход |
|---|---|---|---|
| FK не встаёт | `SQL State 23503`, `violates foreign key constraint` | да | §1–2: пре-чек + `--stub-parents` / `--delete-test-data` |
| дубли под unique | `23505` | нет | руками, с владельцем данных |
| NULL под not null | `23502` | нет | руками, с владельцем данных |
| номер версии занят двумя ветками | `checksum mismatch for migration version N` | да, часто | §2a: `--checksum-version N --apply`, разработчику — перенумеровать |
| объект уже есть, записи нет | `SQL State 42701`, `column … already exists` | да, часто | §2c: `--mark-applied N --reference-stand M` |
| в БД версия, которой нет в образе | `Detected applied migration not resolved locally` | нет, но состояние бывает | §2d |
| миграция помечена упавшей | `Detected failed migration to version N` | нет | снять запись `--checksum-version N --apply`, затем починить причину |
| джоба не запускается вовсе | в логе деплоя нет таски миграций | — | у сервиса не включены миграции — нужен сервис-владелец схемы (§0) |

## 2c. «already exists» — объект в схеме есть, записи в истории нет

Самый частый класс после checksum. Как выглядит:
```
Migrating schema "orders" to version "002 - add contract signature hash column"
SQL State : 42701
Message   : ERROR: column "hash" of relation "contract_signature" already exists
Statement : ALTER TABLE IF EXISTS orders.contract_signature ADD COLUMN hash VARCHAR UNIQUE
```
⚠️ `IF EXISTS` здесь относится к **таблице**, а не к колонке — миграция неидемпотентна. Откуда
берётся расхождение: DDL накатили руками, либо запись сняли при лечении checksum mismatch (§2a),
либо миграцию уже применяли под другим номером.

Обход — сказать Flyway, что версия применена, скопировав запись со стенда, где она прошла штатно:
```bash
python scripts/migration_fix.py --stand 1 --schema dictionary --mark-applied 49 --reference-stand 5
python scripts/migration_fix.py --stand 1 --schema dictionary --mark-applied 49 --reference-stand 5 --apply
```
Почему копируем, а не пишем свою строку: Flyway сверит `checksum` записи с файлом из образа.
Придуманный checksum превратит «already exists» в «checksum mismatch». На эталонном стенде
checksum корректный. `installed_rank` скрипт пересчитывает под целевой стенд.

Перед `--apply` убедись, что объекты миграции в схеме действительно есть: пометка «применено»
ничего не проверяет, и следующая миграция, рассчитывающая на них, упадёт уже по другой причине.
Долгое решение — попросить переписать миграцию на `ADD COLUMN IF NOT EXISTS`.

Номер версии можно писать как `49` или `049` — скрипт сравнивает и строкой, и численно
(в истории версии часто хранятся с ведущими нулями).

## 2d. «В БД есть версия, которой нет в образе»

Состояние, которое остаётся после тестовой раскатки веток: на стенде применены миграции ветки,
а образ `latest` собран из основной ветки и их не содержит.

Ожидаемое поведение Flyway при валидации — `Detected applied migration not resolved locally`.
Но падает ли на этом конкретный мигратор, зависит от его конфига (`validateOnMigrate`,
`outOfOrder`, `ignoreMigrationPatterns`). Утверждать, что стенд «заминирован», без прогона
нельзя: проверяется прогоном, а не рассуждением.

Если падение случится — обход как в §2a: снять лишнюю запись (`--checksum-version N --apply`)
либо дождаться мёржа ветки, после которого версия появится в образе и вопрос закроется сам.

## 2e. Что ещё держать в голове (не воспроизводили)

- **Две джобы одной схемы одновременно.** Деплой запускает все сервисы разом; если владельцев у
  схемы двое, Flyway возьмёт advisory-lock, и вторая джоба будет ждать или упадёт по таймауту.
  Обход: сервисы с миграциями одной схемы катить по очереди.
- **Большое отставание стенда.** Полсотни накопленных миграций могут не уложиться в таймаут —
  джоба умрёт с `Resource creation timed out`, хотя ничего не сломано. Обход: посмотреть в
  пре-чеке число pending и катить, понимая, что первая попытка может не успеть.
- **Откатить миграцию нельзя.** Undo в Flyway Community нет: если миграция применилась, а сервис
  потом упал, схема уже изменена. Обход — только новая миграция, поэтому пре-чек дешевле любого
  разбора после.

## 3. Миграция задачи не поедет — подмена образа мигратора

Фикс данных этого не решает: образ `latest` собран из основной ветки. Два выхода — выбор за
человеком, оба надо озвучить до деплоя:

1. **Мёрж ветки мигратора в основную** — вопрос разработчику задачи. Дальше обычный деплой.
2. **Подмена тега образа в тестовой ветке конфигурации** — процедура ниже. Правка чужого
   репозитория конфигурации — только с явного разрешения.

### 3.1 Тег образа мигратора — из Bamboo, без доступа в registry

```bash
GET /rest/api/latest/plan/{MIGRATOR_PLAN}/branch?max-result=200          # branch-план ветки задачи
GET /rest/api/latest/result/{branchPlanKey}?max-results=5                # его зелёные билды
GET /rest/api/latest/result/{buildKey}?expand=variables,vcsRevisions
#   переменная с тегом релиза (напр. release_params.tag) → готовый тег
#   vcsRevisions[].vcsRevisionKey → коммит; сверить с HEAD ветки мигратора
```
Формат тега обычно задаёт переменная плана, например
`maven.version = 1.0.${bambooBuildNumber}-${bambooBranchSequence}`: для branch-плана суффикс —
номер плана, для основной ветки — её имя. Теги по билдам не перезаписываются.

**Проверь, что образ действительно выложен** (а не только «должен был собраться») — по логу:
```bash
GET /rest/api/latest/result/{buildKey}?expand=stages.stage.results.result.logEntries&max-results=4000
#   ищем: "The push refers to repository [...]"  и  "<tag>: digest: sha256:… size: …"
```
⚠️ **Ловушка, стоившая ложной тревоги:** в логе buildx две разные строки про образ.
`naming to {registry}/{extra-segment}/{image}:<tag>` — внутреннее имя стадии, путь там может
быть **с лишним сегментом**. Реальный адрес выкладки печатает
`The push refers to repository [{registry}/{image}]` — именно он совпадает с тем, что
подставляет шаблон конфигурации. Ориентируйся на `push refers` + `digest`, не на `naming to`.

Заодно из лога сборки основной ветки видно, что `latest` — это её же образ (`<tag>` и `latest` с
одним digest), а branch-билд `latest` не трогает. Поэтому подмена тега в тестовой ветке не
задевает деплои с основной конфигурацией.

### 3.2 Куда класть правку: ветка по номеру тестовой подзадачи

Если деплой ищет ветку конфигурации по номеру задачи из имени релиза (`config-branch.md`),
рабочая схема, не трогающая пространство имён разработчика:

1. ветка конфигурации называется по подзадаче тестирования (`PROJ-200`), а не по задаче;
2. правка одной строки в шаблоне Job миграций: `{image}:latest` → `{image}:{tag}`;
3. **новый релиз сервиса с именем этой же подзадачи** (`PROJ-200-1`) из того же зелёного билда —
   без этого деплой будет искать ветку по номеру задачи и уедет на основную;
4. деплой, затем в логе проверить строку «найдена ветка: PROJ-200».

Почему так лучше, чем ветка по номеру задачи: релизы разработчика (`PROJ-123-*`) продолжают ехать
с основной конфигурацией и не подхватывают тестовый тег; после тестирования ветку можно удалить,
ничего не откатывая.

**База ветки: конфиги задачи + правка, а не только правка.** Тестовая ветка должна содержать всё,
что задача уже привезла в конфигурацию, иначе деплой поедет с тестовым мигратором, но без
пропертей задачи. Перед созданием проверь ветку родительской задачи и ответвляйся от неё:

```bash
GET .../repos/{config-repo}/branches?filterText={NUMBER}&limit=20     # искать по НОМЕРУ — имена разнородные
POST .../repos/{config-repo}/branches
     {"name":"{SUBTASK}","startPoint":"refs/heads/{ветка задачи или master}"}
```
Нашлась ветка задачи → `startPoint` = она; не нашлась → основная, и это нормально: у задачи нет
своих конфигов. Вывод пиши в отчёт явно, чтобы человек видел, на чём собрана тестовая ветка.

Ветка может уже существовать — тогда переиспользуй, но сверь, от чего она стоит:
```bash
GET .../repos/{config-repo}/compare/changes?from=refs%2Fheads%2F{BRANCH}&to=refs%2Fheads%2Fmaster&limit=100
#   0 файлов → ветка = основная (своих изменений нет)
GET .../repos/{config-repo}/compare/commits?from=refs%2Fheads%2F{BRANCH}&to=refs%2Fheads%2Fmaster
#   какие коммиты есть в ветке и нет в основной — видно, чьи это правки
```

Правка через REST, без клона:
```bash
GET  .../repos/{config-repo}/raw/{path}?at=refs%2Fheads%2F{BRANCH}          # забрать файл
GET  .../repos/{config-repo}/commits?until=refs%2Fheads%2F{BRANCH}&limit=1  # sourceCommitId = HEAD ветки
PUT  .../repos/{config-repo}/browse/{path}    multipart: content, message, branch, sourceCommitId
```
После коммита сверь строку в ветке И в основной: основная обязана остаться с `:latest`.
Если правка не проходит по правам (401/403), остаётся только путь 1 — мёрж разработчиком.

**После прогона тестовую ветку удали.** **Разработчику скажи:** на проде миграция обязана попасть
в основную ветку мигратора раньше или одновременно с релизом сервиса, иначе код обратится к
отсутствующему объекту и запросы упадут.

## 4. Проверка, что миграция реально поехала

`deploymentState: SUCCESS` не значит, что схема стенда изменилась. Проверь четыре вещи:

1. строка выбора ветки конфигурации в логе деплоя (если делали подмену образа);
2. в логе джобы `Successfully validated N migrations`: N = число файлов **основной ветки**, а
   миграция задачи живёт только в её ветке → на стенд она **не поехала**;
3. запись `V###` в `{schema}.flyway_schema_history`
   (`select version, installed_on from {schema}.flyway_schema_history order by installed_rank desc limit 3`);
4. сам объект в `information_schema` (колонки миграции либо есть, либо нет) и заполненность данных,
   если миграция делала backfill — прогони её `case` как `SELECT` ещё до раската, это покажет,
   сколько строк останется без значения.

Пока колонок нет, тестировать функционал задачи бессмысленно: код из ветки ждёт их и будет
падать «багами», которых в задаче нет. Сообщи это человеку до начала тестирования.
