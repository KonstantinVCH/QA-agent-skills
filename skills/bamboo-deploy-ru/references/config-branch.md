# Ветка конфигурации по имени релиза: автоподбор, пины, алиасы

Читать, если ваш деплой-скрипт подхватывает ветку репозитория конфигурации (Ansible
inventory/group_vars, Helm values, kustomize) по имени релиза. Если такого механизма нет и
деплой всегда идёт с основной ветки конфигурации — этот файл не нужен.

Содержание: 1) как работает автоподбор; 2) три режима выбора ветки; 3) задеплоить конкретную
ветку, чьё имя не матчится; 4) перекатить сервисы на новую ветку; 5) уборка; 6) ловушки.

## 1. Как работает автоподбор

Деплой-скрипт берёт имя релиза (`PROJ-123-5`), вычленяет номер задачи, ищет в репозитории
конфигурации ветку-кандидат (`PROJ-123`, `feature-PROJ-123`, `feature/PROJ-123`) и
переключается на неё; не нашёл — остаётся основная ветка. Хороший деплой-скрипт печатает это
в лог, например:

```
Cloning into 'deploy-config'...
Для релиза 'PROJ-123-5' найдена ветка конфигурации: PROJ-123
Деплой выполняется из ветки конфигурации: PROJ-123
```

**Проверяй эти строки после каждого деплоя** — это единственное подтверждение, что поехал
правильный конфиг. Нет строки «найдена ветка» → взята основная ветка, и сервис с новыми
пропертями не поднимется (или поднимется со старыми — хуже, потому что молча).

Если ваш скрипт таких строк не печатает — попроси DevOps добавить: без них проверить, какой
конфиг уехал, можно только по отрендеренным файлам на поде.

Следствия:
- **имя релиза значимо**: оно обязано содержать номер задачи, иначе автоподбор не сработает;
  `feature-PROJ-123-6` тоже матчится на ветку `PROJ-123`;
- прав администратора окружений, кук сессии и браузера не требуется — хватает REST-триггера;
- автоподбор работает не везде: переменная-пин на окружении сервиса отключает его и жёстко
  задаёт ветку.

## 2. Три режима — и они смешиваются на одном стенде

Переменная-пин живёт на **окружении сервиса**, а не на стенде. Значения переменных окружения
обычному пользователю через API часто недоступны (403), поэтому режим читается из лога
последнего деплоя:

| Строка в логе | Что значит |
|---|---|
| «ветка задана вручную: X» | пин переменной, автоподбор выключен |
| «для релиза 'R' найдена ветка: X» | автоподбор сработал |
| только «деплой выполняется из ветки: master» | автоподбор ветку задачи не нашёл |

```bash
python scripts/config_branch_alias.py --scan-stand 5                                # таблица по всем сервисам
python scripts/config_branch_alias.py --scan-stand 5 --only order-service,payment-service
python scripts/config_branch_alias.py --from <ветка> --as PROJ-123 --check-env <environmentId>
```

- «ПИН на нужную ветку» → делать нечего, просто перекатить релизы;
- «ПИН на основную ветку» → это не «ветки нет», а выключенный автоподбор: сервис останется без
  конфига задачи, что бы ни было в имени релиза. Нужен DevOps — очистить переменную или
  выставить её в ветку задачи;
- «автоподбор работает» → дальше §3.

Типичная живая картина на одном стенде: пять сервисов запинены на `PROJ-123-FOR-TESTING`, два —
на основную ветку, ещё два работают автоподбором и нашли `PROJ-123`. То есть три механизма
одновременно — фразу «стенд на ветке X» говорить нельзя, только «сервис Y на ветке X».

## 3. Просят задеплоить конкретную ветку — это делается, а не отклоняется

Автоподбор — удобство, а не ограничение прав. Если ветка есть, а её имя не подходит под
паттерн (`TMP-TEST-PROJ-123`, `PROJ-123-FOR-TEST`, произвольное), **нельзя отвечать «не
соответствует критериям, поставлю основную»**: человек просил конкретный конфиг, а основная
ветка — молча не то, что просили.

**Шаг 0 — режим каждого затронутого сервиса** (`--scan-stand` или `--check-env`, §2).

**Шаг 1 — имя ветки уже матчится** → обычный деплой, потом проверить строку в логе.

**Шаг 2 — имя не матчится: ветка-алиас.** Второе имя для того же коммита; содержимое не
копируется и не меняется, исходная ветка не трогается.
```bash
python scripts/config_branch_alias.py --from TMP-TEST-PROJ-123 --as PROJ-123 --check-env <envId>          # план
python scripts/config_branch_alias.py --from TMP-TEST-PROJ-123 --as PROJ-123 --check-env <envId> --apply  # после «да»
```
Затем релиз с именем `PROJ-123-N` из зелёного билда → деплой → строка выбора ветки в логе.

Проверено сквозным прогоном: алиас от основной ветки, релиз с именем алиаса, деплой одного
сервиса → в логе «найдена ветка: <алиас>», SUCCESS за минуту, алиас после прогона удалён.

**Шаг 2a — имя алиаса занято другой веткой.** Частый случай: ветку задачи доработали
(`PROJ-123-FOR-TESTING` выросла из `PROJ-123`), а каноничное `PROJ-123` живёт своей жизнью и
его тянут другие сервисы. Перезапись сломала бы им деплой, поэтому скрипт берёт свободную метку
`PROJ-990NN` и печатает, что имя релиза теперь `PROJ-99001-N`. Ветку ищет автоподбор по имени
релиза, поэтому метка работает так же, как номер настоящей задачи.

Создание ветки в репозитории конфигурации — чужой репозиторий: покажи план человеку и получи
«да», как на любом гейте. Отдельный токен не обязателен: без `BITBUCKET_TOKEN` скрипт берёт
логин из git credential helper.

**Шаг 3 — алиас создать не вышло** (нет прав): скажи прямо и предложи два пути — попросить
DevOps выставить переменную-пин на нужную ветку либо запустить деплой через форму ручного
(custom) деплоя, если в вашем Bamboo она есть: там ветка задаётся полем.

## 4. «Перекатай сервисы, где нужна кастомная конфигурация, с новой ветки»

Список даёт `--scan-stand N`: катить надо те, у кого в колонке «откуда ветка» стоит ветка
задачи или пин на неё. Нужен ли новый релиз — зависит от того, что изменилось:

| Что поменялось в репозитории конфигурации | Что делать |
|---|---|
| в ту же ветку долили коммиты | повторный деплой того же релиза — ветка читается заново при каждом деплое |
| ветка **другая по имени** (`PROJ-123` → `PROJ-123-FOR-TESTING`) | при автоподборе — новый релиз с подходящим именем или алиас (§3); при пине — правка переменной у DevOps |

Сервисы с пином на основную ветку в список не попадают, пока переменную не поправят, — иначе
они молча уедут без конфига задачи. После каждого деплоя — строка выбора ветки в логе.

## 5. Уборка

Алиас и временные тестовые ветки после прогона удалить: это указатели, исходная ветка и
коммиты остаются.
```bash
curl -X DELETE -H "Authorization: Bearer $BITBUCKET_TOKEN" -H "Content-Type: application/json" \
  -d '{"name":"refs/heads/PROJ-123","dryRun":false}' \
  "$BITBUCKET_URL/rest/branch-utils/latest/projects/{CONFIG_PROJECT}/repos/{config-repo}/branches"
```

## 6. Ловушки

1. **Имя новой тестовой ветки вида `TMP-TEST-PROJ-123` или `PROJ-123-FOR-TEST`** — поедет
   основная ветка. Имя должно совпадать с номером задачи из имени релиза точно. Проверено
   тремя живыми деплоями:

   | Релиз | Что было в репозитории конфигурации | Что подхватил деплой |
   |---|---|---|
   | `PROJ-101-4` | только `TMP-TEST-PROJ-101` | основная |
   | `PROJ-102-3` | только `PROJ-102-FOR-TEST` | основная |
   | `PROJ-103-1` | `PROJ-103` **и** `TMP-TEST-PROJ-103` | `PROJ-103` |

   Это правило про то, как называть **новую** ветку. Если ветка с «неподходящим» именем уже
   существует и её просят задеплоить — это не отказ: §3, алиас.
2. **Логика матчинга часто живёт в Script-таске Bamboo**, а не в репозитории конфигурации:
   поиск по репозиторию её не найдёт, правило подтверждается только прогонами.
3. **Тестовая ветка от основной, когда у задачи уже есть своя ветка конфигурации** — стенд
   получит твою правку, но без пропертей задачи. Перед созданием ищи ветку задачи **по номеру**,
   не по полному имени: имена в таких репозиториях разнородные (`PROJ-123`, `feature/PROJ-123`,
   `TMP-TEST-PROJ-123`, `PROJ-123-FOR-TEST`, `TEMP_FOR_TESTS-PROJ-123`).
4. **`SUCCESS` без строки «найдена ветка»** — не успех: конфиг мог уехать с основной ветки.
5. **Пин на основную ветку принимают за «ветки нет»** и создают алиас — он ничего не даст, пока
   переменную не очистят. Скрипт с `--check-env` такой `--apply` не выполнит.

### Исторический контекст

До появления автоподбора ветку конфигурации выбирали через форму ручного деплоя (плагин custom
deployments): она требовала куку сессии и XSRF-токен, API переменных окружения отдавал 403, а
REST-триггер всегда давал основную ветку. Если в старых логах видно такое поведение — это оно.
