## Почему файл мок-профиля ничего не включает

Самая дорогая ошибка на этом шаге — решить, что мок применён, потому что файл с мок-адресами
существует. По умолчанию сервис едет на **реальный dev-адрес партнёра** из конфига окружения.

Найди в скриптах деплоя условие включения мок-профиля. В разобранном примере (функция деплой-скрипта,
подмешивающая мок-переменные) оно требовало трёх вещей одновременно:

1. переменная деплоя (условно `config_environment`) содержит подстроку `mock` (по умолчанию `default`);
2. окружение — тестовое или предпрод (на prod моки невозможны);
3. существует файл `mocks/<slug репозитория сервиса>`.

Переменные из мок-файла перекрывали одноимённые из конфига окружения, плюс появлялся флаг
вида `mocks_enable: true`.

Практическое следствие: обычный REST-триггер деплоя эту переменную не передавал, то есть деплой
ехал **без моков**. Поэтому и появился маршрут A.

## Два маршрута

| | **A. точечное переопределение URL** (по умолчанию) | **B. включение мок-профиля флагом деплоя** |
|---|---|---|
| Что правим | конфиг окружения конкретного стенда: URL партнёра → адрес мока | файл мок-профиля сервиса |
| Ветка репозитория конфигов | ветка задачи `PROJ-123` | ветка задачи или основная |
| Как катим | обычный деплой; ветка конфигов подхватывается по имени релиза (скилл `bamboo-deploy-ru`) | деплой с переменной мок-профиля (в примере — Custom Deployment в Bamboo) |
| Браузер | не нужен | в примере нужна была сессия Bamboo: PAT на форму давал 302 на SSO, API переменных окружения — 403 |
| Область действия | ровно те переменные, что прописали | все переменные мок-профиля разом |

Маршрут A стоит по умолчанию не потому, что он «правильнее», а потому что укладывается в обычный
деплой целиком: те же токены, тот же триггер, ничего не надо нажимать руками.

Маршрут B выигрывает, когда мок-профиль уже лежит в основной ветке и надо быстро включить его
целиком — и так же быстро выключить.

⚠️ У маршрута A бывает неочевидное требование: если ветка конфигов определяется по имени релиза,
релиз должен называться по ветке. Когда задача не трогает репозиторий сервиса, релиз всё равно
придётся создать (из сборки основной ветки) и назвать `PROJ-123-*` — иначе поедет конфиг основной
ветки. Этот случай на практике не проверялся.

## Имена файлов и расхождение портов

Соглашения об именах файлов конфигов бывают неочевидными. В разобранном примере каталог в
`group_vars` назывался slug-ом репозитория **с дефисами**, а файл внутри — **с подчёркиваниями**:

```
group_vars/payment-gateway-adapter/payment_gateway_adapter_test_2
mocks/payment-gateway-adapter
```

Мок-файл — плоский фрагмент YAML, только переопределяемые ключи:

```yaml
# mocks/payment-gateway-adapter
payment_gateway_url: 'http://{WIREMOCK_HOST}:18005/gateway_api'
payment_gateway_security_enabled: 'false'
```

Если мок-адрес записан в двух местах (конфиг стенда и мок-профиль), порт **всегда** сверяй в обоих:
их расхождение уже было причиной дефекта — резервный сервис смотрел на порт мока соседнего
продукта. Факт даёт только трейс (`jaeger_urls.py`).

## OAuth/OIDC-провайдер

Экран входа через внешнего провайдера часто формирует **не тот сервис**, который потом забирает
данные пользователя. В разобранном случае адрес провайдера для редиректа задавался у
сервиса-шлюза авторизации, а у сервиса интеграции — только адрес API данных. Переключение одного
сервиса интеграции оставило на экране реальный адрес провайдера: первый перекат стенда ушёл впустую.

Разделение ролей: шлюз авторизации формирует редирект на провайдера и обменивает код, сервис
интеграции забирает данные пользователя (userinfo, документы). Для полного флоу нужны оба.

Два разных мока, которые легко перепутать:

| Мок | Что отдаёт |
|---|---|
| OAuth2/OIDC-мок (шаблон WireMock для OAuth2) | `/auth/authorize` (форма логина), `/auth/token`, `/auth/introspect`, `/userinfo`, `.well-known` |
| мок API данных провайдера | документы и прочие данные пользователя + негативные варианты → 400 |

Признак, что OAuth2-заглушка встала: на экране входа появляется
«Simulated OAuth2 / OpenID Connect login service, powered by WireMock» — email и любой пароль,
реальные креды не нужны.

⚠️ После переключения провайдер на стенде **не настоящий**: проверки реальной интеграции веди на
других стендах и предупреди об этом команду.

## Возврат на реальный адрес

- маршрут A — передеплоить сервис с основной ветки конфигов;
- маршрут B — тот же деплой со значением переменной по умолчанию (`config_environment=default`).

Откат маршрута B в разобранном примере на практике не проверялся: логически он возвращает
состояние основной ветки, но прежде чем обещать его команде, прогони и подтверди трейсом
(`jaeger_urls.py`).

Стабы и фикстуры мока откатываются отдельно и раньше — см. шаг 8 основного скилла.
