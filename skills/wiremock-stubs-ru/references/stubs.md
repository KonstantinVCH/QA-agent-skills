## Перечень эндпоинтов

Мок-режим переводит на заглушку **все** исходящие вызовы сервиса к партнёру. Не застабленный путь
отдаёт `404 Request was not matched`, и прогон падает посреди флоу на «недоступности партнёра»,
которой нет. Поэтому перечень собирается до написания стабов, а не по ходу.

Основной способ — скрипт, он же достаёт методы:

```bash
python scripts/adapter_paths.py <источник> -o paths.txt
python scripts/wm.py cover <мок> paths.txt
```

**Репозиторий сервиса часто не склонирован** — на этом сверка покрытия и проваливается. Источников
три, результат одинаковый (проверено: три источника дают побайтово равный вывод):

| Источник | Когда |
|---|---|
| `<путь к каталогу>` | репо склонирован локально |
| `<файл>.zip` | не склонирован: в Bitbucket/GitHub кнопка Download на ветке, архив передать как есть, распаковывать не надо |
| `<slug> --pat <PAT>` | скрипт скачает архив ветки из Bitbucket Server сам (`--branch`, по умолчанию `master`; нужны `BITBUCKET_URL`, `BITBUCKET_PROJECTS`) |

Понимаются оба вида архивов — и с файлами в корне (как отдаёт Bitbucket), и с одной обёрточной
папкой сверху (GitHub).

`adapter_paths.py` разбирает две распространённые схемы объявления путей в Spring-сервисах и
сообщает, какая сработала:

| Схема | Где живут пути | Что делает скрипт |
|---|---|---|
| A. конфиг | `application.yml` → `<префикс>.clients.<партнёр>.path.<ключ>` | берёт пути из конфига, метод — из кода (`.post()` стоит над `.path(...getCreatePayment())`) |
| B. литерал | в коде: `.path("/v1/partner/order/add")` | берёт путь и метод из одной цепочки |

Другая схема (Feign, RestTemplate, другой язык) — перечень собрать вручную grep-ом по коду
HTTP-клиента и записать в тот же формат `МЕТОД /путь`, по строке на эндпоинт.

**Метод важен ровно так же, как путь.** Стаб на `POST` при вызове `GET` отдаёт 404, и это
неотличимо от «партнёр не ответил». В конфиге методов нет — если скрипт вывел `ANY`, метод надо
посмотреть в коде глазами.

Скрипт печатает ещё две вещи из того же блока конфига, и они нужны для дизайна стабов:
`timeouts.response` — граница, выше которой задержка стаба проверяет обработку таймаута, а не
просто «медленного партнёра»; `retry.max-attempts` — сколько состояний должно быть у сценарного
стаба, чтобы дойти до успеха.

Отдельно проверь, что клиент не один: у сервиса, кроме основного партнёра, бывает, например,
сервис нормализации адресов (`/clean/address`), и он попадает под мок-режим тем же деплоем.
Внутренние клиенты платформы мокать не надо — перечисли их в `ADAPTER_INTERNAL_CLIENTS` или
`--internal`, скрипт их отфильтрует.

Чем перечень добирается, когда скрипт дал не всё:

```bash
python scripts/jaeger_urls.py <сервис> <стенд>   # реально вызванное + мок это или нет
python scripts/wm.py log <мок> --unmatched       # дырки, которые вылезли на прогоне
```

Jaeger даёт факт, но не полноту: у одного сервиса за 7 дней нашлось 8 трейсов и **ни одного**
исходящего вызова самого сервиса. Как источник перечня он не годится — как доказательство
переключения незаменим.

⚠️ Считай только спаны **своего** сервиса. В трейсе участвуют десятки сервисов, и если брать все
client-спаны подряд, чужие вызовы припишутся твоему: так однажды «нашлись» обращения к сервису
адресов и к внутреннему toolbox, которых проверяемый сервис не делает. `jaeger_urls.py`
фильтрует по владельцу спана и показывает, сколько чужих отбросил.

Соседний мок того же партнёра/продукта — эталон стиля имён и набора негативов: `wm.py stubs <мок>`.

## Спецификация метода

Код даёт пути и методы, но не даёт **тела ответов, коды и обязательность полей** — а стаб без них
получается выдуманным: `{"status":"ok"}` вместо того, что реально отдаёт партнёр. Настоящий
контракт лежит в документации интеграции (Confluence, OpenAPI партнёра, вики команды), и там для
каждого метода обычно есть готовые примеры сообщений.

Удобная конвенция, если команда ведёт её в Confluence: родительская страница — интеграция,
дочерние — по одной на метод, заголовок вида `[N.] МЕТОД <сервис>/<путь> - описание`. Нумерация в
заголовке отражает порядок вызовов, то есть готовую нумерацию для имён стабов
(§[Имя стаба](#имя-стаба)). Фактическую конвенцию своего проекта запиши в `project-config.md`.

Через MCP Atlassian, если подключён, иначе REST Confluence через curl:

```
confluence_search: type=page AND space={CONFLUENCE_SPACE} AND title ~ "POST <сервис>"
confluence_get_page_children(parent_id=<страница интеграции>)   # весь перечень методов сразу
confluence_get_page(page_id=<метод>)
```

Что забирать со страницы метода:

| Блок | Зачем для стаба |
|---|---|
| **Обмен**: синхронный / асинхронный | асинхронный = ответ придёт колбэком, нужен `postServeActions` webhook, а не только тело |
| **Входные / выходные параметры**: JSON или **XML** | у части партнёров обмен XML по XSD-схеме — стаб с JSON-телом не подойдёт |
| **Примеры входящего / исходящего сообщения** | готовое тело для `response.body`, с реальными форматами полей |
| **http-status** в примере ответа | какой код ставить в стаб |
| **Аутентификация** (Basic Auth, токен) | нужен ли стаб на `/auth` и заголовок в матчере |
| **Настройки метода** | таймауты партнёра — та же граница, что `timeouts.response` в конфиге |
| **Алгоритм работы** | шаги, на которых партнёр отвечает ошибкой, — из них берутся негативные варианты |

⚠️ **Пример сообщения важнее таблицы параметров.** Однажды таблица объявляла поле
`payer/address/countryCode`, а пример в том же документе — `country_code`. Правда оказалась в
примере и в коде: camelCase молча игнорировался, и данные сохранялись чужие. Таблицы устаревают,
примеры копируют из реальных прогонов.

⚠️ **Поле «Имя сервиса» в карточке метода может врать.** Страницы клонируют из шаблона и правят
заголовок, забывая поля: в карточке метода одного сервиса может стоять имя соседнего.
Ориентируйся на заголовок страницы и на код, а поле «Имя сервиса» перепроверяй.

Спека полезна и до написания стабов: если в ней сказано, что метод вызывается **однократно** и
запрос воспроизводится curl-ом, мок может не понадобиться вообще (см. шаг 1 основного скилла и
[inbound.md](inbound.md)).

## Имя стаба

Пример соглашения команды (своё — в `project-config.md`):

```
N. Бизнес-описание на русском            основной сценарий
N. Бизнес-описание (вариант)             отклонение
```

Нумерация отражает порядок взаимодействия с партнёром. Пример мока платёжного шлюза:

```
1. Создание платежа                                   POST /payments
2. Ответ на событие                                   POST /api/eventStatus
3. Подтверждение платежа                              POST /payments/confirm
4. Подтверждение платежа (шлюз недоступен)            503, сценарий, состояние Started
5. Подтверждение платежа (успех после повтора)        200, состояние second-attempt
```

Ключ задачи, английский и техжаргон в имя не идут: мок живёт годами и переживает задачу, а читать
список приходится тому, кто про неё не знает. Перед созданием посмотри `wm.py stubs` соседнего
мока и повтори его стиль.

## Матчинг запроса

- `urlPath` + `queryParameters` — предпочтительно: `{"key": {"matches": ".*"}}`.
- `url` — точное совпадение пути **и** query-строки: `"/v1/partner/download?key"` матчит только
  пустое значение `key`. Отсюда заглушки, которые «работают» на одном заказе.
- `urlPathPattern` — когда в пути идентификатор: `"/payments/[^/]+/status"`. Конкретный номер в
  пути превращает стаб в одноразовый.
- Матчеры: `equalTo`, `matches` (regex), `contains`, `equalToJson`, `matchesJsonPath`, `absent`,
  `doesNotMatch`.
- `priority` (1 — высший) решает конфликты пересекающихся стабов.

## Шаблоны Handlebars

Контексты разные, и это стоило команде дня работы:

| Где | Что работает | Что не работает |
|---|---|---|
| тело и заголовки ответа (нужен `"transformers": ["response-template"]`) | `{{request.query.X}}`, `{{jsonPath request.body '$.X'}}` | `originalRequest` |
| URL и тело **webhook** (`postServeActions`) | `{{originalRequest.query.X}}`, `{{jsonPath originalRequest.body '$.X'}}` | `request` |

Неизвестная переменная рендерится в **пустую строку** — без ошибки и без записи в лог, так что
сломанный шаблон выглядит как «просто не работает», а в приёмник уходит `?param=`. Проверяется
только опытом: залить стаб → сделать запрос → `wm.py log <мок> -n 1 --full` и смотреть
фактическое тело ответа.

`response-template` включается на весь ответ: любые `{{…}}` в теле начинают интерпретироваться,
включая те, что должны были уйти литералом.

## Минимум вариантов

Стаб, который всегда отвечает 200, не проверяет обработку ошибок — а именно она обычно и ломается.
К каждому пути заведи хотя бы один негатив:

| Вариант | Как |
|---|---|
| Ошибка партнёра | второй стаб, `status: 500/503`, имя `(шлюз недоступен)` |
| Таймаут | `response.fixedDelayMilliseconds` больше `timeouts.response` из конфига |
| Медленный ответ | та же задержка, но меньше таймаута |
| Восстановление после сбоя | сценарий, ниже |
| Отказ по конкретному полю | `bodyPatterns` + `matchesJsonPath` |

Задержка сдвигает всю последующую ветку интеграции — этим ловятся гонки, которые в проде
маскирует медленная реальная интеграция, а мгновенная заглушка провоцирует.

## Сценарные стабы

```json
{ "name": "4. Подтверждение платежа (шлюз недоступен)",
  "priority": 1, "scenarioName": "payment-confirm-retry",
  "requiredScenarioState": "Started", "newScenarioState": "second-attempt",
  "request": { "method": "POST", "urlPath": "/payments/confirm" },
  "response": { "status": 503 } }
```

Второй стаб — тот же `scenarioName`, `requiredScenarioState: "second-attempt"`, `status: 200`.

Сценарным стабам нужен приоритет выше, чем у обычного стаба того же пути, иначе обычный
перехватит запрос первым и состояние никогда не сдвинется. Перед прогоном —
`wm.py reset-scenarios <мок>`, иначе сценарий стартует с середины прошлого прогона.

Число шагов сверяй с `retry.max-attempts` сервиса: при `max-attempts: 3` сценарий из двух
состояний проверит восстановление, из четырёх — уже не успеет.

## Вебхуки

```json
"postServeActions": [{ "name": "webhook", "parameters": {
  "method": "POST",
  "url": "http://<сервис>.{STAND}.example.test/openapi/decision",
  "headers": { "Content-Type": "application/json" },
  "body": "{\"paymentId\": {{jsonPath originalRequest.body '$.payment.id'}}}",
  "delay": { "type": "fixed", "milliseconds": 2000 } }}]
```

Если в одном моке перечислено несколько приёмников (по стенду на каждый), вебхук уходит веером на
все — адрес приёмника проверяй внимательно, чужой стенд получит колбэк по чужому заказу. В
WireMock 2.x нет `subEvents`, поэтому результат вебхука виден только на приёмнике: Jaeger или логи
пода (скилл `opensearch-logs-ru`).

## Негатив по заголовку

Переименовать стаб на время прогона — правка общего контура, которую легко забыть откатить. Где
заголовок можно проставить (прямой вызов сервиса, автотест), лучше стаб с `priority: 1`, который
матчится только по опт-ин заголовку:

```json
{ "priority": 1,
  "request": { "method": "POST", "urlPath": "/payments/confirm",
               "headers": { "X-Test-Scenario": { "equalTo": "gateway-down" } } },
  "response": { "status": 503 } }
```

Пока заголовка нет — работает штатный стаб, чужие прогоны не ломаются. Приём из открытого скилла
[`petrkindlmann/qa-skills@service-virtualization`](https://skills.sh/petrkindlmann/qa-skills/service-virtualization).
Если запрос формирует сервис и заголовок не добавить — остаётся переименование, но тогда это
фикстура с обязательным откатом.
