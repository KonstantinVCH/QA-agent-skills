# Форматы для разработчика

Дополнение к шаблону слоя 2 из SKILL.md. Примеры — на вымышленном интернет-магазине
(`order-service`, `payment-service`, `notification-service`, адаптеры партнёров доставки).

## Содержание

1. Развёрнутая форма (шесть подписей)
2. Заголовок: атомарность ЧТО / ГДЕ / УСЛОВИЯ

4. Самопроверка перед выдачей
5. Ложные баги: тест-данные и грязный стенд

## 1. Развёрнутая форма

Для сложных находок, где причина неочевидна и нужен контраст с работающим аналогом. Шесть
подписей строго в этом порядке:

```
Что вижу:  <конкретный наблюдаемый симптом> + [ссылка на трейс с ?uiFind=<span>]
Когда:     <точный вход / эндпоинт / партнёр / состояние / ветка>
Как должно быть: <ожидаемое> — и СРАЗУ на основании чего: класс.метод (+строка) ИЛИ спека
Похоже, причина: <гипотеза> + контраст с работающим аналогом (где то же самое работает)
Чем кончается: <бизнес-следствие> + точный лог/ошибка (дословно, в блоке кода)
Fix:       <конкретное исправление>
```

Правила формы:
- «Что вижу» — симптом, «Чем кончается» — следствие; не смешивать.
- Причину помечать «Похоже» / «Возможно», если корень в рантайме не пойман.
- Контраст «у аналога работает» — сильный аргумент, включать, если есть.
- Симптом якорить фактом из трейса (тайминг, статус, лог), а не пересказом.

Пример:

```
Что вижу: 6 повторов подряд за ~0.5 с в консьюмере очереди delivery.address-check (order-service). [трейс ?uiFind=<span>]
Когда: подтверждение заказа с курьерской доставкой — POST /order/confirm, если проверка адреса не за сегодня → отложенная ветка «перезапросить проверку и дождаться».
Как должно быть: пауза 30 с между повторами — её задаёт код: AddressCheckProducer.scheduleCheck ставит заголовок x-delay=route.getMinBackoff() (в трейсе x-delay=30000, попыток 6); паузу должен отрабатывать delayed-exchange.
Похоже, причина: exchange delivery.address-check в AddressCheckDelayedListener объявлен без type (по умолчанию direct), а direct игнорирует x-delay. Остальные exchange сервиса — delayed (RabbitMQConfiguration, стр. 61), у них пауза работает: в том же трейсе OrderCancelEvent с x-delay=3600000 реально ждёт.
Чем кончается: 6 попыток сгорают меньше чем за секунду, а ответ проверки адреса приходит на ~7-й секунде — не успевает. Заказ уходит в службу доставки без результата проверки, с логом:
  Address check is not ready after 6 attempts for orderId 128112, sending confirm without addressCheckResultId
Fix: объявить delivery.address-check delayed-exchange, как остальные, — x-delay сработает, пауза 30 с даст проверке время ответить.
```

## 2. Заголовок: атомарность ЧТО / ГДЕ / УСЛОВИЯ

Заголовок — одна строка `ЧТО — ГДЕ — при каких условиях`. Это первое, что читает разработчик;
тело — раскрытие.

- **ЧТО** — конкретный объект: поле, метод, сообщение, значение.
- **ГДЕ** — конкретный компонент: консьюмер, класс.метод, exchange.
- **ПРИ УСЛОВИЯХ** — конкретный триггер: действие, состояние.

Хорошие заголовки:
- `пауза между повторами не работает: 6 повторов за ~0.5 с вместо 30 с — в консьюмере delivery.address-check — при отложенной проверке адреса`
- `addressCheckResultId приходит null — в маппере адаптера ConfirmRequestMapper — при отправке поля под именем checkResultMessageId`

Антипаттерн: «ЧТО: имя поля не совпадает — шлюз шлёт A, адаптер читает B» — вся история
засунута в одно поле.

Перегруженный заголовок:

**Плохо:** `Составной заказ не завершается после оплаты: при оплате дочернего заказа
payment-service отправляет родителю несуществующий статус ORDER_COMPLETED — всегда 520, ошибка
молча глотается`

В заголовок засунуты симптом, причина, код ошибки и механизм разом; суть тонет.

**Хорошо:** `Составной заказ не завершается после оплаты дочернего заказа` — а дальше в теле:
что вижу, когда, как должно быть, причина.

## 3. Комментарий разработчику в Jira

```
@<разработчик>, привет!

<Одно предложение: ЧТО не работает — наблюдаемое поведение>.
<Условие/шаги: при каком вводе/состоянии>.
Ожидалось: <требование> — согласно <ссылка на спеку, шаг N>.
<Причина из кода, если найдена: класс/метод/условие + почему>.
<трейс: {JAEGER_URL}/trace/<traceId>?uiFind=<spanId>>
```

Обязательные элементы:
- конкретное обращение — тот, кто отвечает за этот код;
- факт: воспроизведено, а не «кажется»;
- требование со ссылкой и номером шага спеки;
- причина из кода (класс.метод + условие) либо прямое «предполагаю в <место>, требует проверки»;
- доказательство — ссылка на трейс.

Комментарий публикуется только после явного «да» пользователя.

## 4. Самопроверка перед выдачей

1. Поймёт ли новый человек суть, прочитав только заголовок и первые 3 строки?
2. Можно ли сократить заголовок вдвое без потери смысла?
3. Можно ли вынести половину техдеталей вниз без потери пользы?
4. Не смешаны ли симптом, причина и fix в одном предложении?
5. Не написан ли разбор первопричины (RCA) там, где нужен понятный баг-репорт?

Хотя бы одно «да, можно упростить» — переписать.

## 5. Ложные баги: тест-данные и грязный стенд

Подтверждённый механизм — ещё не доказательство, что дефект возникает в реальном флоу.

- **Грязное состояние.** «Профиль не обновляет ФИО после входа через внешнего провайдера»
  оказалось артефактом четырёх прогонов подряд с SQL-откатами. Чистый парный прогон (негатив +
  контрольный позитив на тех же данных) опроверг находку.
- **Своё же тест-тело.** «Точно баг, 500 в getDeliveryDocs»: тестировщик слал `POST /order/confirm`
  телом без `customerId`, маппер берёт `request.customerId` из тела → `null` создал он сам.
  Реальные вызовы на стендах `customerId` передают. Подтверждение механизма (null → 500) не
  доказывает, что null возникает в реальном флоу.

Писать «точно баг» — только после исключения тест-данных и с прямым доказательством.

Как исключить:
- сравнить своё тело запроса с реальным вызовом того же метода из трейса соседнего прогона;
- прогнать контрольный позитив на тех же данных, отличие — в одном поле;
- вернуть стенд в исходное состояние перед повтором.
