## 1. Базовые правила подготовки

- Проверяй данные чтением (MCP PostgreSQL или `psql` на чтение) **до** любых изменений.
- Рядом с каждым INSERT/UPDATE сразу пиши откат (DELETE / UPDATE к исходным значениям) и сохраняй
  исходные значения SELECT-ом.
- **Сообщение в очередь:** перед публикацией прочитай JSON-схему сообщения (где лежат схемы —
  `references/project-config.md`, раздел 4). Типы полей — строго по схеме: строка вместо числа или
  лишнее поле дают ошибку десериализации, которую легко принять за баг.
- **Тела запросов не выдумывай** — бери из реальных вызовов (раздел 2).
- Один прогон — свой клиент и чистая сессия браузера. Чужая сущность, открытая в живой сессии,
  может привязаться к клиенту из этой сессии; фоновый поллинг открытой вкладки продолжает менять
  данные. Закрывай браузер после прогона. Эталонные данные держи отдельно от расходных.
- Узнай, где живёт сущность на каждом шаге флоу. Пример: заказ до авторизации покупателя может
  жить только в кэше (Redis), и пустые таблицы после первого вызова `create` — норма, а не баг.

## 2. Откуда брать тела запросов

Порядок источников — по убыванию достоверности:

1. **Лог реального вызова в трейсе.** Если трейсинг прикрепляет к спанам тела HTTP (например,
   Logbook: span-лог «Incoming Request … POST … {body}») — там лежит то, что действительно ушло на
   стенд. Как достать — `references/live-run-techniques.md`, раздел 2.
2. **Шаги и вложения тест-кейсов** в системе тест-менеджмента: готовые тела, SQL-фикстуры, порядок
   вызовов.
3. **Коллекции запросов** (Bruno / Postman): только **структура** — эндпоинт, набор полей, порядок
   шагов во флоу.

Коллекции часто никто не обновляет: продукты, клиенты, партнёры и окружения там протухают.
Прогон на протухшем клиенте даёт ложный отказ, который потом ищут в коде. Поэтому данные из
коллекций считай устаревшими, пока не подтвердил SELECT-ом по стенду.

**Обратное пополнение.** Получил новое рабочее тело, прошедшее живую проверку, — подготовь файл
запроса по образцу соседних в коллекции и предложи человеку добавить. Коммит и пуш в репозиторий
коллекций — только по явному подтверждению.

## 3. «Нет данных» — это задача, а не итог

«На стенде нет сущностей этого продукта» — повод их создать. Записывать проверку в непроверенные
можно только после трёх источников, строго в этом порядке:

1. **База знаний / вики проекта** — как вообще создаётся сущность по продукту: флоу, предусловия,
   обязательные поля, фича-тоглы, партнёры, ловушки. Ищи по названию продукта и синонимам
   (рус + англ + аббревиатура). Без этого непонятно, что именно создавать.
2. **Система тест-менеджмента** — тест-кейсы по продукту. Ищи не только по названию и Feature, но
   и по шагам сценария и description: флоу часто виден только в шагах.
3. **Коллекции запросов** — структура вызовов и порядок шагов (с оговоркой из раздела 2).

Все три источника пусты и данные действительно не создать — тогда фиксируй непокрытие с
конкретной причиной («партнёр не реализовал метод», «нет мока партнёра», «нужна живая подпись»), а
не формулировкой «нет данных». «Нет данных» читается как дыра в покрытии и всплывает на проде, хотя
почти всегда данные создаются известным команде способом.

## 4. Барьеры на штатном пути и приёмы обхода

Барьер — тоже не приговор. Разобранные случаи:

| Барьер | Приём обхода |
|---|---|
| Формирование документа падает: у партнёра записи пуст обязательный код, а колонка `NOT NULL` | подменить партнёра **у конкретной записи** (договора, заказа) временной фикстурой с откатом; справочник не трогать — найти SELECT-ом партнёра, у которого код заполнен |
| Фича-тогл продукта выключен | выясни, чем управляет тогл. Часто — клиентским путём создания, а не обработчиком: создай сущность фикстурой и вызови серверный endpoint обработчика (например, callback решения в адаптере партнёра) — дальше сервис отработает сам |
| Нужна авторизация через внешнего провайдера в браузере | войди во флоу с той точки, где начинается серверная часть, пропустив клиентскую |
| У тестовой записи пусты обязательные поля таблицы отчётов | падение называет конкретную колонку — дозаполняй точечно, каждое следующее падение сужает список |

**Граница обхода.** Обход не меняет общие данные, от которых зависят чужие прогоны (справочники,
фича-тоглы, чужие активные сущности). Своё — меняем. Общее — только временно, с фиксацией исходного
значения и обязательным откатом. Нельзя обойти без правки общих данных — спроси человека.

Фикстура допустима для состояния, которого живой путь не даёт. Заполняй в ней явно все
типизированные колонки (enum, статусы, флаги), а не копируй соседнюю строку целиком: скопированные
служебные поля тащат чужое состояние. Прогон только на фикстурах — не тестирование задачи:
сначала воспроизведи эталонный E2E-сценарий живым путём, фикстуры — сверх него.

## 5. Запись в БД и откат

MCP-серверы PostgreSQL часто настроены только на чтение. Для записи используй `psql` (например, в
docker) или драйвер (`psycopg2`) с DSN из переменной окружения:

```bash
docker run --rm -i postgres:16 psql "$DB_DSN" < fixture.sql
```

В Git Bash на Windows добавь `MSYS_NO_PATHCONV=1` перед командой, иначе пути и DSN исказятся.

Порядок для каждой фикстуры:

1. SELECT исходного состояния → сохрани результат (это эталон отката).
2. INSERT/UPDATE фикстуры с уникальной меткой прогона (например, `external_id = 'qa-PROJ-123-<время>'`),
   чтобы потом найти и удалить ровно своё.
3. Прогон.
4. Откат: DELETE своих строк по метке, UPDATE изменённых к эталону.
5. SELECT после отката → результат совпадает с эталоном.

**Откат не всегда возвращает всё.** SQL-откат UPDATE может не вернуть служебные и hash-влияющие
поля (`hash_code`, `update_date`, `record_end_date` и подобные). Следующий прогон тогда ложно «не
обновляет данные»: сервис видит «не изменилось» и пропускает запись. Откатывай все поля, которые
трогал сервис, а не только бизнес-статус. При малейшем сомнении делай чистый одиночный прогон на
гарантированно исходном клиенте, а не доверяй цепочке прогонов с откатами.

## 6. Ловушки тестовых данных

- **Значение есть в БД, но нет в enum кода.** Колонка-строка в БД может содержать значение, которого
  нет в Java-enum (старое, ручное). Подставишь его в фикстуру — получишь
  `InvalidDataAccessApiUsageException` при чтении сущности. Допустимые значения бери из enum в
  коде ветки задачи, а не из `SELECT DISTINCT`.
- **Невалидные идентификаторы.** Контрольные суммы (ИНН, номер карты по Луну, страховые номера),
  реальные коды справочников (адресные коды, коды регионов), формат UUID для id состояний. Список
  ловушек вашего домена — `references/project-config.md`, раздел 7.
- **Пропущенное опциональное поле.** Тело тест-запроса без поля, которое в проде всегда шлёт
  вызывающий, даёт null внутри сервиса и ложный NPE/500. Сверяй тело с реальным вызовом.
- **Данные под условия спеки.** Чтобы доказать расхождение со спекой, нужен клиент, чьё состояние БД
  удовлетворяет **всем** условиям спеки, плюс контрольный позитив на тех же данных.
