# Оформление бага, разбор находки и сообщения людям

Читай на Шагах 8.3–8.4. Полный формат оформления бага с эталонами и двухслойной подачей — скилл
`bug-report`; если он установлен, оформляй баг по нему. Здесь — ядро правил, которого
достаточно, чтобы не ошибиться и без него.

Цель — адресат понимает проблему за 20 секунд. Формально точный текст, который трудно понять с
первого чтения, написан плохо и переписывается. Это правило приоритетнее «красивой техничности»:
оно появилось после реплик коллег «не понял», «очень сложно понять», «это очень нагружено» — каждый
раз текст был верным по сути и нечитаемым по форме.

Перед оформлением бага — `references/false-bug-checklist.md`. **Публикация в трекер или вики —
только по явному «да, публикуй».** Черновик готовь и показывай всегда.

## 1. Порядок изложения — строго такой

1. **Что сломано** — наблюдаемый симптом простыми словами.
2. **Когда проявляется** — условие, триггер, вход.
3. **Как должно быть** — со ссылкой на источник (спека, код, контракт).
4. **Чем это кончается** — пользовательское или бизнес-последствие.
5. **Причина** — только если подтверждена кодом или трейсом.
6. **Fix** — отдельной короткой строкой, не смешивая с симптомом.

Не пытайся уместить симптом, условие, причину, код ошибки, трейс и fix в одну фразу или в один
перегруженный заголовок. Это главная ошибка, из-за которой текст приходится переписывать.

**Правила простого языка:**

- Заголовок содержит только `ЧТО сломано + ГДЕ / ПРИ КАКОМ УСЛОВИИ`. Причина, код ошибки, имя метода и
  fix одновременно в заголовке запрещены.
- Первые две строки понятны человеку **без чтения кода**.
- Одна фраза — одна мысль. Симптом, причина, следствие и fix — в разных предложениях.
- Техдеталь, не нужная для понимания сути, уходит вниз.
- Можно сократить без потери смысла — сократи. Можно упростить без потери точности — упрости.
- **Никакой изобретённой терминологии.** Термина, которого нет в задаче, спеке или речи команды,
  быть не должно. Проверка: этот термин кто-то из команды произносил, или он только мой?

**Запрещено:** начинать с класса, метода, enum или кода ошибки, если проблему можно объяснить
по-человечески; заголовок длиной в абзац; в одном абзаце — что сломалось, почему, как починить и
какие смежные правки нужны; тащить смежные идеи и рефакторинги в основной текст (они идут в блок
«Отдельно обсудить»).

## 2. Кому пишем

- **Аналитику / менеджеру:** бизнес-язык, эффект, статусы, варианты решения. **Без** классов,
  методов, номеров строк, traceId, внутренних enum и кодов ошибок, если их не просили.
- **Разработчику:** сначала короткая человеческая суть, потом точное место (`класс.метод`, условие),
  трейс, лог, рецепт фикса.
- **Адресат не указан** → коротко и понятно, техдетали после сути.

Двухслойность полезна даже для одного адресата: сначала слой 1 (4–6 строк, которые поймёт новый
человек в команде без чтения кода), затем слой 2 (место в коде, код ошибки, traceId, подтверждённая
причина, fix). Показывай слой 1 первым.

## 3. Шаблон по умолчанию и краткая форма

```
Заголовок: <что ломается и где>

Что вижу:        <1 короткое предложение простым языком>
Когда:           <условие>
Как должно быть: <ожидание + источник>
Чем кончается:   <последствие>
Причина:         <если подтверждена>
Fix:             <1 короткая строка, если уместно>
Трейс:           <ссылка>
```

**Краткая форма для чата и трекера:**

```
Получаю <точная ошибка / HTTP-код> в <метод / эндпоинт>
<кликабельный трейс: {JAEGER_URL}/trace/{traceId}?uiFind={spanId}>
Условие: <партнёр / продукт / состояние, при котором срабатывает ветка>.
Ожидаемо: <что должно быть> — <ссылка на спеку / контракт>.
Фактически: <точный текст ошибки / значение> → <последствие>.
Возможная причина: <класс.метод + строка + почему>.
```

Правила формы:

- **Первая строка — конкретная ошибка, а не следствие.** Ошибка — это точный симптом: текст
  исключения, HTTP-код, код ошибки, строка лога либо измеримое отклонение («6 попыток за 0,5 с
  вместо 30 с между ними»). Бизнес-следствие («заказ уходит без номера платежа») идёт в
  «Фактически», а не в заголовок.
- «Ожидаемо» ссылается на источник: страница спеки, контракт метода, документация. Не «должно
  работать», а «по <ссылка> ожидается X».
- Трейс — с `?uiFind=` на конкретный span или метод, а не просто на трейс.
- «Причина» — если подтверждена кодом (прочитаны класс и строка). Выведена, но в рантайме не
  поймана — «Возможная причина».
- Текст ошибки — дословно (`NumberFormatException: For input string: "null"`), не пересказ.

## 4. Развёрнутая форма

Шесть подписей строго в этом порядке:

```
Что вижу:        <конкретный симптом> + [трейс с ?uiFind=<span/метод>]
Когда:           <точный вход / эндпоинт / партнёр / состояние / ветка>
Как должно быть: <ожидаемое> — и СРАЗУ на основании чего: класс.метод(+строка) ИЛИ страница спеки
Похоже, причина: <гипотеза> + контраст с рабочим аналогом (где то же самое работает)
Чем кончается:   <бизнес-следствие> + точный лог / ошибка (дословно, в code-блоке)
Fix:             <конкретное исправление>
```

**Заголовок = одна строка `ЧТО — ГДЕ — при каких условиях`.** Пример:

- `пауза между ретраями не работает: 6 попыток за ~0,5 с вместо 30 с — в консюмере очереди проверки платежа — при отложенной ветке подтверждения заказа`

**Атомарность полей.** ЧТО — конкретный объект (поле, метод, сообщение, значение). ГДЕ — конкретный
компонент (консюмер, `класс.метод`, exchange). ПРИ УСЛОВИЯХ — конкретный триггер. Антипаттерн:
«ЧТО: имя поля не совпадает — сервис A шлёт X, адаптер читает Y» — это вся история в одном поле.

«Что вижу» — симптом, «Чем кончается» — следствие, не смешивай. Причину помечай «Похоже» /
«Возможно», если корень в рантайме не пойман. Контраст «у аналога работает» — сильный аргумент.
Симптом якори фактом из трейса (тайминг, статус, лог), а не пересказом.

```
Что вижу: 6 ретраев подряд за ~0,5 с в консюмере очереди payment.validation (payment-service). [трейс ?uiFind=<span>]
Когда: подтверждение заказа — POST payment-service/api/order/confirm, если результат проверки платежа не за сегодня → ветка «перезапросить проверку и дождаться».
Как должно быть: пауза 30 с между ретраями — её задаёт код: PaymentValidationProducer.scheduleCheck ставит заголовок x-delay = minBackoff (в трейсе x-delay=30000, попыток 6); паузу должен отрабатывать delayed-exchange.
Похоже, причина: exchange payment.validation объявлен без type (по умолчанию direct), а direct игнорирует x-delay. Остальные exchange сервиса объявлены как delayed — у них пауза работает (в том же трейсе другое событие с x-delay=3600000 реально ждёт).
Чем кончается: 6 попыток сгорают меньше чем за секунду, а ответ проверки приходит через ~7 с. Заказ подтверждается без номера проверки, с логом:
  Payment validation is not ready after 6 attempts for orderId 128112, confirming without validationResultMessageId
Fix: объявить payment.validation как delayed-exchange, как остальные, — тогда x-delay сработает.
```

**Антипример перегруженного заголовка.**
Плохо: `Групповой заказ не завершается после оплаты: при подтверждении вложенного заказа сервис
отправляет групповому заказу несуществующий статус COMPLETED_PAID — всегда 520, ошибка молча
глотается` — симптом, причина, код ошибки и механизм разом, суть тонет.
Хорошо: `Групповой заказ не завершается после оплаты вложенного заказа` — остальное в теле.

## 5. Разбор находки для человека (парный прогон)

Когда показываешь результат проверки или объясняешь баг в чате:

```
# Кейс: <одна фраза, что проверяем>
**Контекст:** стенд {STAND} · сервис, ветка PROJ-123 (commit) · клиент {id}

### Предусловия (состояние БД ДО, проверено SELECT)
<конкретные SQL с фактическими значениями>
+ вывод: почему эти данные удовлетворяют / не удовлетворяют условиям спеки

### Шаги
Шаг 1. <что послал> — ПОЛНЫЙ запрос / payload. Объясни, откуда такое сообщение берётся в
реальной жизни (кто отправитель в проде, какой поток или очередь).
  Ожидаемый результат (по спеке, со ссылкой на шаг спеки): ...
  Фактический результат: HTTP-код + текст ошибки + что в БД. Кликабельный трейс.
Шаг 2. КОНТРОЛЬНЫЙ ПРОГОН — позитив на тех же данных, отличие в одном поле.
  Ожидаемый / фактический + трейс.

### Вывод — сводная таблица
|                    | Прогон 1 | Прогон 2 |
| БД (одна и та же)  | ...      | ...      |
| Ожидание по спеке  | ...      | ...      |
| Факт               | ✅       | ❌       |
+ одна фраза: единственная разница между прогонами; причина в коде; риск для прода.
```

Правила подачи:

1. **Язык простой, без сжатых формулировок.** Каждый термин объясняй при первом употреблении:
   «входящее сообщение» → кто его шлёт, куда, как выглядит (покажи тело с пометкой, где нет поля).
2. **«По спеке должен пройти» — только после проверки ВСЕХ условий спеки на тестовых данных.**
3. **Различай «в памяти» и «в БД».** «Маппер затирает поле» вызовет вопрос «где в БД затёртая
   запись?». Говори точно: затирание в загруженной JPA-сущности до валидации; в БД изменение не
   попадает (rollback, в трейсе нет UPDATE-спанов).
4. **Ссылайся на лог трейса как на доказательство противоречия:** «сервис сам прочитал эту запись
   (SELECT на 18-й мс), но ответил "не найдена"» — сильнее пересказа кода.
5. **Каждый прогон — кликабельный трейс**; перед публикацией убедись, что в трейсе видно именно то,
   что утверждаешь (тело запроса, SQL-параметры, ответ).
6. **Короткая версия для чата** — одна фраза «спека проверяет X, код проверяет Y; из-за этого <кто>
   падает с <ошибка> при <условие>» + риск + пара трейсов (позитив / негатив).

## 6. Комментарий разработчику в задаче

```
@<разработчик>, привет!

<Одно предложение: ЧТО не работает — наблюдаемое поведение>.
<Условие / шаги: при каком вводе или состоянии>.
Ожидалось: <требование> — согласно <ссылка на спеку, шаг N>.
<Причина из кода, если найдена: класс / метод / условие + почему>.
<трейс: {JAEGER_URL}/trace/{traceId}?uiFind={method}>
```

Обязательно: обращение к тому, кто отвечает за этот код; факт (воспроизведено, а не «кажется»);
требование со ссылкой и номером шага; причина из кода либо честное «предполагаю в <место>, требует
проверки»; трейс со ссылкой.

## 7. Самопроверка перед выдачей

1. Поймёт ли новый человек суть по заголовку и первым трём строкам?
2. Можно ли сократить заголовок вдвое без потери смысла?
3. Можно ли вынести половину техдеталей вниз без потери пользы?
4. Не смешаны ли симптом, причина и fix в одном предложении?
5. Не написан ли RCA / техзаключение там, где нужен понятный текст о баге?

Хотя бы одно «да, можно упростить» — перепиши.
