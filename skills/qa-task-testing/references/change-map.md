# Карта изменений по задаче — PR, ветки, diff

Читай на Шаге 3.0, до любого вывода о том, что есть или чего нет в коде.

## Зачем это отдельный протокол

Вывод «в коде нет X» — утверждение высшей ответственности. Ложное «нет в коде» дезинформирует
команду и подрывает доверие к QA. Два типичных провала:

- Заявили «метод получения связанных лиц не реализован», проверив три репозитория и diff двух
  коммитов, но не открыв список PR. Метод лежал в трёх PR соседних репозиториев.
- Вывод «метод проверки баланса нигде не вызывается» сделали по локальному чекауту, стоявшему на
  основной ветке. Метод был добавлен коммитом в ветке задачи — diff по API это подтвердил.

Общая причина: смотрели не туда и остановились рано. Локальный чекаут по умолчанию стоит на
основной ветке, а задача почти всегда живёт в ещё не смерженной ветке. `git log --grep=PROJ-123` по
основной ветке ничего не найдёт, даже если PR давно открыт. **Пустой результат — сигнал «ищу не
там», а не доказательство «кода нет».**

Пока протокол ниже не выполнен полностью, статус любого вывода о реализации — строго
**HYPOTHESIS** с пометкой «PR/коммиты не проверены полностью». Формулировку «в коде нет» не
используй.

Примеры ниже — для Bitbucket Server (REST API 1.0). Доступ: `BITBUCKET_URL`, `BITBUCKET_TOKEN`
(HTTP access token с правом чтения). Подробнее об API — документация Bitbucket Server REST. Для GitHub
и GitLab логика та же: найти PR/MR по ключу задачи во всех репозиториях, взять полный diff ветки
против основной (`gh pr list --search "PROJ-123" --state all`, `gh pr diff`; GitLab —
`/api/v4/projects/{id}/merge_requests?search=PROJ-123&state=all`, `/repository/compare`).

---

## Шаг A — Найти все PR и ветки во всех репозиториях

```bash
H="Authorization: Bearer $BITBUCKET_TOKEN"

# 1. PR по задаче в каждом репозитории (state=ALL — включая смерженные и отклонённые)
curl -fsSL -H "$H" "$BITBUCKET_URL/rest/api/1.0/projects/{PROJECT}/repos/{REPO}/pull-requests?state=ALL&filterText=PROJ-123&limit=10"

# 2. PR нет — искать ветку
curl -fsSL -H "$H" "$BITBUCKET_URL/rest/api/1.0/projects/{PROJECT}/repos/{REPO}/branches?filterText=PROJ-123"
```

Заголовки PR часто прямо называют добавленные методы — это самый дешёвый источник карты.

**Перебирай не только очевидные репозитории.** Основные сервисы — не весь список. Метод для
админки может лежать в отдельном BFF-сервисе, DTO — в общей модели, логика партнёра — в адаптере.
Полный перечень репозиториев — в `references/project-config.md`, раздел 4.

Запросы по разным репозиториям отправляй **параллельно**, а не по очереди.

## Шаг B — Взять diff

```bash
# diff PR
curl -fsSL -H "$H" "$BITBUCKET_URL/rest/api/1.0/projects/{PROJECT}/repos/{REPO}/pull-requests/{PR_ID}/diff"

# полный diff ветки против основной — НЕ diff двух произвольных коммитов
curl -fsSL -H "$H" "$BITBUCKET_URL/rest/api/1.0/projects/{PROJECT}/repos/{REPO}/compare/changes?from=refs/heads/PROJ-123&to=refs/heads/master"

# конкретный коммит, если известен hash
curl -fsSL -H "$H" "$BITBUCKET_URL/rest/api/1.0/projects/{PROJECT}/repos/{REPO}/commits/{hash}/changes"
```

Diff между двумя произвольными коммитами легко теряет файлы — сравнивай ветку с основной целиком.

Из ответа извлекай: `diffs[].source.toString` (имя файла), `diffs[].hunks[].segments` (строки
`REMOVED` / `ADDED`), контекст вокруг изменения (сегменты `CONTEXT`).

**Почему REST, а не локальный git.** `git fetch --all` на больших монорепозиториях подвисает и
таймаутит, локальный клон бывает неполным и неактуальным. Ветка или hash известны — тяни diff
напрямую по API: быстрее и надёжнее.

Работаешь с локальным чекаутом — перед любым Grep/Read проверь `git branch --show-current` и
`git log -1`, а перед разбором «как сейчас в коде» сделай `git pull --ff-only origin <ветка-задачи>`.
`git fetch` и просмотр `origin/...` рабочую копию не обновляют — grep будет читать старьё.

## Шаг C — Разобрать каждый изменённый файл

По каждому production-файлу ответь:

1. **Что за класс/метод?** — полный путь и пакет.
2. **Что изменилось?** — буквально, строки REMOVED → ADDED.
3. **Где используется?** — поиск по репозиторию (`/browse?q={methodName}` или локальный grep по
   ветке задачи) либо контекст из diff.
4. **Побочные изменения?** — тесты, конфиги, другие файлы в том же PR.

Собери сводную таблицу и только после неё делай выводы:

| Репозиторий | PR / ветка | Файл | Метод | Что изменилось |
|---|---|---|---|---|

## Шаг D — Записать в базу знаний (если она есть)

Смысл в том, чтобы в базе лёг **реальный код изменения**, а не пересказ описания задачи.
Заметка о сервисе есть → дополни её секцией; сервиса в базе нет → создай заметку. Правила ведения
графа — скилл `obsidian-llm-wiki`.

````markdown
### Изменение PROJ-123 — {краткое описание} ({дата деплоя})

**Файл:** `путь/до/Файл.java`

```diff
- старая строка
+ новая строка
```

**Контекст:** {что за класс, зачем константа/метод}
**Используется в:** {методы/классы из context-строк diff}
**PR:** ссылка | **Commit:** hash
````

Ссылки ставь в обе стороны: заметка сервиса → заметка задачи, заметка задачи → каждый
затронутый сервис, связанный термин → обновить.

## Чеклист

- [ ] Проверены ВСЕ репозитории, где есть ветка задачи, — включая общие модели и BFF админок
- [ ] Открыт список PR (`state=ALL`), а не только верхушка ветки
- [ ] Сделан полный diff ветка ↔ основная ветка
- [ ] Для каждого изменённого **production**-файла изменение разобрано (и записано, если ведётся база)
- [ ] Тестовые изменения отмечены отдельно: попутный рефакторинг или логика
- [ ] DOC_GAP зафиксирован, если diff расходится с документацией
- [ ] Ссылки в базе знаний расставлены в обе стороны

## Быстрые ссылки (Bitbucket Server)

```
PR list:  /rest/api/1.0/projects/{PROJECT}/repos/{REPO}/pull-requests?state=ALL&filterText=PROJ-123
PR diff:  /rest/api/1.0/projects/{PROJECT}/repos/{REPO}/pull-requests/{ID}/diff
Compare:  /rest/api/1.0/projects/{PROJECT}/repos/{REPO}/compare/changes?from=refs/heads/{branch}&to=refs/heads/master
Raw file: /rest/api/1.0/projects/{PROJECT}/repos/{REPO}/raw/{path}?at=refs%2Fheads%2F{branch}
Branches: /rest/api/1.0/projects/{PROJECT}/repos/{REPO}/branches?filterText=PROJ-123
Search:   /rest/api/1.0/projects/{PROJECT}/repos/{REPO}/browse?q={methodName}
Auth:     Authorization: Bearer $BITBUCKET_TOKEN
```

Поиск по коду на сервере может быть не проиндексирован. Тогда скачай архив ветки и ищи локально:
отрицательный результат поиска без проверки самого поиска — «поиском не нашёл», а не «в коде нет».

**PR и merge — никогда по своей инициативе.** Создать ветку и коммит по запросу можно; открыть PR,
смержить, запушить в основную ветку или запустить деплой — только по явной команде.
