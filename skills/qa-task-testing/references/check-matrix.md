# Матрица проверок и согласование плана

Читай на Шагах 4–5: составляешь матрицу и готовишь план к согласованию с человеком.

## Откуда берутся строки матрицы

Матрица опирается на результаты Шагов 1–3, поэтому без них её не составить:

- **Шаг 1** дал ответ «зачем доработка» — отсюда валидационные проверки: решена ли реальная
  проблема, а не только «сделано как написано».
- **Шаг 2** дал требования спеки — каждое требование становится секцией матрицы.
- **Шаг 3** дал карту изменений — каждый изменённый метод и каждое место его использования
  становятся кандидатом в проверку или регресс.

Охвати четыре класса:

| Класс | Что проверяем | Пример (сервис заказов) |
|---|---|---|
| happy path | основной сценарий требования | заказ с оплатой картой переходит в `PAID` |
| negative | отказ на невалидном входе / состоянии | оплата отклонена → заказ остаётся `PENDING`, клиенту уходит уведомление |
| edge cases | границы, пустые и null-поля, повторы, гонки | повторный callback оплаты не создаёт второй платёж |
| regression | соседнее поведение, которое правка могла задеть | другие способы оплаты и места, где читается изменённое поле |

Метод проверки: `API` / `SQL` / `Trace` (Jaeger) / `MQ inject` (сообщение в очередь) / `UI`.

## Формат матрицы

```
| # | Требование (источник) | Проверка | Метод | Данные и предусловия | Ожидаемый результат (источник) | Evidence | Статус |
|---|---|---|---|---|---|---|---|
```

Правила:

- **Каждый негатив — в паре с контрольным позитивом** на тех же данных, отличие в одном поле.
  Негатив без пары ничего не доказывает (принцип 4).
- **Ожидаемый результат ссылается на источник:** страница спеки и шаг, контракт метода,
  `класс.метод:строка`. «Должно работать» — не ожидаемый результат.
- **Данные — реальные и проверенные:** id из SELECT по стенду, а не «какой-нибудь клиент».
- **Тело запроса — из реального вызова** (см. `references/preconditions-and-test-data.md`).
- **Evidence** заполняется на прогоне: traceId, результат SQL, ответ API. До прогона столбец пуст.
- **Статус:** `PASS` / `FAIL` / `INCONCLUSIVE` / `BLOCKED` / `NOT RUN`. INCONCLUSIVE не превращай в
  PASS — разберись.

Если задача трогает интеграцию с внешним партнёром (адаптер, колбэк, мок) — до матрицы выполни
инвентаризацию `references/integration-readiness.md`. Матрица на фикстурах при неготовой
интеграции проверяет маппинг на твоих данных, а не задачу.

## Согласование плана (Шаг 5)

Покажи человеку план по шаблону `assets/plan-for-approval.md` и дождись явного «go». До него на
стенде разрешены только чтения: SELECT, GET без побочных эффектов, чтение трейсов и конфигов.

Почему это жёсткое правило. Реплика «прогони» звучит как разрешение, но человек ещё не видел, какие
данные ты собираешься менять и на каком клиенте. Реактивный прогон уже приводил к тест-кейсам с
данными, которых на стенде не существовало.

Что должно быть в плане:

1. Матрица проверок (формат выше).
2. Предусловия: какие данные уже есть (SELECT с фактическим результатом), какие придётся создать.
3. Какие изменения на стенде будут сделаны: SQL-фикстуры, сообщения в очередь, стабы моков —
   и **откат к каждому**.
4. Риски: чьи данные можно задеть, что общее (справочники, фича-тоглы) придётся менять временно.
5. Что останется непроверенным и почему — предметно («нет мока партнёра», «нужна живая
   подпись»), а не «нет данных».

## Итоговый статус матрицы

После прогона матрица превращается в комментарий с доказательствами — формат
`assets/coverage-comment.md`. Каждая строка PASS там имеет полный запрос, фактический результат из
БД и кликабельный трейс.
