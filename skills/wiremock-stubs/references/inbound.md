# Мока быть не может: играем внешнюю систему сами

Читать, когда на шаге 1 основного скилла выяснилось, что интеграция **входящая** — партнёр зовёт
твой сервис, а не наоборот. WireMock подменяет только исходящие вызовы, поэтому заглушки здесь нет и
не будет. Но задача решается, и обычно быстрее, чем моком.

## Как понять, что случай этот

Три быстрых факта, любой из них достаточен:

```bash
python "$SK/scripts/wm.py" apis --grep <партнёр>          # мока нет в реестре (Studio)
python "$SK/scripts/jaeger_urls.py" <сервис> <стенд>      # исходящих вызовов самого сервиса нет
```

и главный — карточка метода в спецификации: поле вроде **«Вызывающий сервис» = внешняя система**.
Там же лежат **примеры входящего сообщения** — то самое тело, которое надо послать.

⚠️ **Про авторизацию спека и практика могут расходиться.** Бывает, что в спеке написано «должна
быть настроена Basic Auth», а метод на тестовом стенде отвечает без заголовка авторизации (так
было проверено на чтении; требует ли авторизацию запись — отдельный вопрос). Если прилетит 401,
добавь `--basic user:pass` и уточни креды у разработчика сервиса.

## Общий рецепт

Схема одна для любого входящего метода: взять из спеки готовый пример тела, подставить свои
идентификаторы, послать, **прочитать результат обратно**.

```bash
# 1. тело из «Примеры входящего сообщения» спеки -> body.json (utf-8)
# 2. отправить, подставив идентификаторы прогона
python "$SK/scripts/post_json.py" <url метода> body.json \
       --set orderId=<свежий id> --set payer.last_name=ИВАНОВ

# 3. прочитать обратно: 2xx сам по себе ничего не доказывает
python "$SK/scripts/post_json.py" "<url чтения>?<параметр>=<id>" --get
```

`post_json.py` нужен вместо `curl` по той же причине, что `wm.py`: тела таких запросов почти всегда
содержат русские ФИО и адреса, а `curl -d` из Git Bash отправляет их как `U+FFFD`, и данные молча
сохраняются битыми. Скрипт отправляет JSON с `ensure_ascii=True` — по проводу идёт `\uXXXX`.
Полезные флаги: `--dry-run` (посмотреть, что уйдёт), `--basic user:pass`, `-H "X-Api-Key: …"`,
`-X PUT`, `--get`, `--set-json путь=JSON` для нестроковых значений.

Негативный сценарий получается тем же инструментом: послать тело без обязательного поля, с
несуществующим идентификатором, с неверной подписью — и посмотреть, что ответит твой сервис. Это
ровно то, что дал бы негативный стаб, только без заглушки.

## Пример: колбэк платёжного провайдера

Направление: браузер покупателя уходит на страницу оплаты провайдера, провайдер постит результат
оплаты в `payment-service`. Твой бэкенд к провайдеру наружу за этим результатом не ходит —
исходящих вызовов самого сервиса в трейсах ноль. Мокать нечего.

**Шаг 1.** Открыть страницу заказа → экран выбора способа оплаты. Из `href` кнопки оплаты взять
идентификатор сессии оплаты (`paymentSessionId`, uuid в конце) и `returnUrl` (значение параметра,
через `decodeURIComponent`). **Кнопку не нажимать** — клик уводит на реальную страницу провайдера.

**Шаг 2.** Послать то, что прислал бы провайдер. Эталонное тело — в тестовых ресурсах репозитория
сервиса (`src/test/resources/...`) или в примере из спеки:

```bash
python "$SK/scripts/post_json.py" \
  http://payment-service.{STAND}.example.test/openapi/paymentCallback \
  callback-body.json --set paymentSessionId=<uuid со шага 1>
```

Минимальное тело (ключи `payer` — в той нотации, что в **примере** спеки, см. ловушки):

```json
{ "provider": "test-pay",
  "paymentSessionId": "<uuid со шага 1>",
  "status": "SUCCEEDED",
  "amount": { "value": "1490.00", "currency": "RUB" },
  "payer": {
    "last_name": "ИВАНОВ", "first_name": "ПЁТР", "middle_name": "СЕРГЕЕВИЧ",
    "phone_number": "+7 900 000-00-00",
    "card": { "masked_pan": "220000******0004", "expiry": "12/30" } } }
```

**Шаг 3.** Контроль, что данные легли, — отдельным чтением. Если метод по спеке возвращает `200`
вне зависимости от результата сохранения, код ответа ничего не доказывает:

```bash
python "$SK/scripts/post_json.py" \
  "http://payment-service.{STAND}.example.test/api/payments?paymentSessionId=<uuid>" --get
```

**Шаг 4.** Открыть `returnUrl` в той же вкладке → фронт запрашивает статус заказа, дальше обычный
флоу.

**Готовый негативный сценарий** — чтение по несуществующему идентификатору сессии: сервис
отвечает своей ошибкой «запись не найдена». Это и есть штатный кейс «данные от провайдера не
получены».

**Что считать успехом** бери из спецификации: какие поля сверяются, какие статусы получают заказ
и платёж, что происходит с прежними данными покупателя.

## Ловушки

**Нотация ключей — по примеру, а не по таблице.** Если в примере `last_name`, `phone_number`, а в
таблице параметров местами camelCase, верь примеру и коду. Ключ в чужой нотации молча
игнорируется, и запись сохраняется с чужими или пустыми данными.

**Идентификатор сессии одноразовый.** Повтор с тем же значением может вернуть `200`, но данные не
перезаписать. На каждый прогон бери свежий идентификатор с перерендеренного экрана.

**`200` не значит «получилось».** У части входящих методов код успешный всегда — результат
проверяется чтением сущности или запросом в БД.

**Невалидные тестовые данные выглядят как дефект кода.** Номер карты не по алгоритму Луна, ИНН или
другой реквизит с неверной контрольной суммой роняют флоу дальше по цепочке — на проверке в
соседнем сервисе, с ошибкой, которая не указывает на данные. Держи в `project-config.md` набор
заведомо валидных тестовых значений для стендов.

**Кириллица через `curl -d` бьётся необратимо** — отправляй `post_json.py` или своим кодом с
`ensure_ascii=True`.
